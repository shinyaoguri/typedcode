# changelog.d — 変更履歴の断片

利用者に見える変更 1 件につき、このディレクトリに断片のファイルを 1 つ置きます。リリースのとき、前回のタグ以降に**追加された**断片が GitHub Release のノートになります。根拠は [ADR-0055](../docs/adr/0055-release-channels-and-calendar-versioning.md) (版の正本はタグと GitHub Releases で、リリースはリポジトリのファイルを変えない)。

## 名前

`<slug>.<category>.md`

- **slug**: 変更を表す kebab-case の短い名前 (英小文字・数字・ハイフン)。例: `fix-tab-name`
- **category**: ノートのどの節に載るか

| category | ノートの節 |
|---|---|
| `breaking` | 破壊的変更 |
| `feature` | 新機能 |
| `fix` | 修正 |
| `perf` | 性能 |
| `docs` | ドキュメント |

## 本文

- ノートにそのまま載る文として、利用者の言葉で書く (内部の関数名や実装の経緯ではなく、何が変わって利用者にどう見えるか)
- 複数行・複数段落でもよい。ノートでは 1 つの箇条書きの項目に収まる。HTML コメント (`<!-- … -->`) はノートに載らない
- 破壊的変更 (`breaking`) には、利用者がすることになる移行の手順を書く

## 断片は消さない

リリースの後も断片は残します。どれが今回の分かは git の履歴 (前回のタグ以降に追加されたか) が知っています。消すにはリリースがコミットを作ることになり、「リリースはファイルを変えない」が崩れます。

## 断片が要らない変更

利用者に見えない変更 (refactor / test / chore / ci など) には断片を置きません。断片の無い fix / feat のコミット (main は squash merge なので PR タイトル) は、件名がそのままノートに載ります。断片を必須にする検査はありません。件名のままでは利用者に伝わらない変更に断片を書いてください。断片を足したコミットの件名はノートに載りません (断片の本文が代わりに載る)。

## 検査と下見

- 検査: `npm run lint` (中で `node scripts/release.mjs lint` を走らせる)。名前が形に合わない・本文が空の断片を落とす
- ノートの下見: `node scripts/release.mjs notes` (前回の `v*` タグ以降。`--since <タグ>` / `--to <ref>` で範囲を変えられる。全履歴とタグが要るので、先に `git fetch --tags origin`)
