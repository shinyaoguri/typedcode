# ADR-0051: 作問の正本を手元の教材フォルダに置き、問題・ケース・試験を YAML の定義ファイルで表す

- **Status**: Accepted (#794〜#800・#802・#817・#820 で実装済み。実フォルダでの手動確認は #825)
- **Date**: 2026-11-18
- **Deciders**: @shinyaoguri
- **PR / Commit**: (#793 を閉じる PR)

## Context

`/author` は問題文・スターターコード・入出力例を編集して `.tcexam` / `.tcclass` を書き出すが、状態はメモリ上の Monaco モデルだけにある (`packages/editor/src/authoring/AuthorPage.ts`)。ページを閉じると作問の内容は残らず、ファイル名も `p{n}.c` に固定されている。

教員からは次の要望があった (#792)。

- 手元の教材フォルダを開き、その中のファイルを直接編集・保存したい。共同担当者とは Google Drive などで共有する
- 1 つのフォルダに複数の問題 (予備・未採用を含む) を置き、試験ごとに採用する問題と順序を決めたい
- 問題を単位として別の試験でも使い回したい
- 問題文・初期コード・ヒント・複数の解答例・テストケースを扱い、解答例は通常のプログラムファイルにしたい
- 複数のテストケースを 1 つのファイルにまとめ、入力と期待出力を手軽に編集したい
- 学生には 1 つの配布ファイルを渡したい

前提となる制約:

- editor と verify は Chrome / Edge 専用を前提にしている (editor の AGENTS.md 不変条件 9、verify の File System Access API)。`showDirectoryPicker({ mode: 'readwrite' })` が使える範囲と一致する
- 配布物の形 (`ExamBundleProblem` = `{ problemId, statement, starter?, examples? }`) と、その正準化・ハッシュ (ADR-0012 / ADR-0048) は変えずに済ませたい。変えると旧版の editor との互換の注意が増える
- ADR-0048 は、非公開テストを「配布物とは別のファイルで、同じ `{ name, stdin, stdout }` の形」と決め、比較規則を段階 2 に残した
- 署名鍵と監督コードは、配布物を作る人以外に渡ってはいけない
- C / C++ の実行には時間の上限が無い (時間切れは JS/TS の sandbox と Python だけ)

判断点 D1〜D7 と推奨は #792 のコメントで示し、メンテナが推奨どおり採用した。

## Considered Options

### D1. 教材の表し方

#### Option A: 1 問につき 1 つの定義ファイル (YAML) を置き、本文・コードなどは通常のファイルとして相対パスで参照する

- Pros: 本文は Markdown、コードは `.c` / `.py` のまま他のエディタでも開ける。1 つのフォルダに複数の問題を置け、ファイル名を教員が自由に付けられる。差分が読める
- Cons: 定義と実ファイルの対応が崩れうる (移動・削除)。欠損の検出が要る

#### Option B: 1 問につき 1 フォルダを置き、中のファイル名を固定する (`problem.md`・`starter.c` など)

- Pros: 定義ファイルが要らない
- Cons: 1 つのフォルダに複数の問題を置けない。ファイル名を自由に付けられない。複数の解答例やヒントの順序を表せない

#### Option C: 1 問を 1 つの JSON / YAML にすべて埋め込む

- Pros: 1 ファイルで持ち運べる
- Cons: コードを通常のファイルとして開けない (構文の色付け・実行・他のツール)。長い本文やコードの差分が読みにくい

定義ファイルの書式は YAML にする。ケースの複数行の入出力を、エスケープ無しのブロックスカラーで書けるため。editor は既に `yaml` (v2) を依存に持つ。問題・ケース・試験の 3 種とも YAML にそろえ、パーサを 1 つにする (試験だけ JSON にする案は採らない)。

### D2. テストケースの形

#### Option A: `{ name, stdin, stdout }` に `public?` と `match?` を足し、`public: true` のケースを配布物の `examples` に流す

- Pros: ADR-0048 の入出力例・非公開テストと同じ名前。公開する例と非公開のテストを 1 か所で持てる
- Cons: 教員が `public` を付け忘れると、例が配られない (学生プレビューで気付ける)

#### Option B: `{ name, input, expected }` にする

- Pros: 教員にとって語が分かりやすい
- Cons: 既存の `ProblemExample` と名前が食い違い、変換で取り違えやすい。ADR-0048 の決定と合わない

#### Option C: 公開する入出力例は問題定義に、非公開のテストはケースファイルに分けて持つ

- Pros: 配るものと配らないものがファイルで分かれる
- Cons: 同じ形のデータを 2 か所で編集することになり、一括検証も 2 か所を読む

### D3. 教員用の一括検証の比較規則と実行条件

#### Option A: 完全一致だけ

- Pros: 規則の説明が要らない
- Cons: 末尾の空白や最後の改行の有無だけで不一致になり、本当の誤りと見分けにくい

#### Option B: 既定は「CRLF → LF の後、各行の末尾空白と末尾の空行を無視」、ケースごとに `match: exact` (CRLF → LF だけ) を選べる

- Pros: よくある無害な違いを吸収しつつ、出力の書式を問う問題では完全一致を選べる。途中の空行や行頭の空白の違いは不一致として残る
- Cons: 2 つの規則を説明する必要がある

#### Option C: 空白の並びをすべて区切りとみなして語ごとに比べる

- Pros: 書式の違いにさらに寛容
- Cons: 改行の位置の誤り (1 行に出すべき値を複数行に出す) まで一致にしてしまう

### D4. ヒントの扱い

#### Option A: すぐに配布物に入れる (`ExamBundleProblem.hints?` を足す)

- Pros: 学生に段階的なヒントを出せる
- Cons: shared の型・正準化・パーサ・editor の表示に手が入り、ADR-0048 と同じく旧版の editor との互換の注意が増える。いつ・どう見せるか (最初から / ボタンで開く / 時間で開く) が決まっていない

#### Option B: 最初は配布物に入れず、教員用の資料として保存・編集・プレビューだけ行う

- Pros: 配布物の形を変えずに作問環境を先に出せる。見せ方は使ってから決められる
- Cons: ヒントを学生に届けるには、教員が本文に書き写すか、後の変更を待つ

#### Option C: 書き出し時にヒントを問題文の末尾へ自動で連結する

- Pros: 形を変えずに配れる
- Cons: 問題文とヒントの境目が学生から見えず、見せ方の選択肢も無い

### D5. 問題の共有と版の固定

#### Option A: 「問題を別のフォルダへコピー」で、定義と参照ファイル一式を相対配置ごと複製する。版の固定は書き出した配布物が担う

- Pros: コピー先のフォルダだけで完結する (File System Access API は開いたフォルダの外を読めない)。仕組みが単純
- Cons: コピー元の修正はコピー先に反映されない

#### Option B: 共有の問題ライブラリを別フォルダに置き、試験から参照する

- Pros: 修正が全試験に反映される
- Cons: 開いたフォルダの外を参照することになり、権限とパスの扱いが複雑になる。意図せず過去の試験の内容まで変わる

#### Option C: 問題を ZIP などの持ち運び用の形式に書き出す

- Pros: メールなどでも渡せる
- Cons: 形式が 1 つ増える。フォルダの同期 (Drive) で共有する運用なら要らない

試験ごとに問題を複製して版を固定する仕組みは作らない。配る内容の版は、書き出した `.tcexam` / `.tcclass` そのものが固定している。

### D6. フォルダ無しの作問

#### Option A: 残さない。`/author` はフォルダを開くか作るところから始める

- Pros: 状態の持ち方が 1 つになる。今の作問はメモリ上だけなので、移すデータは無い
- Cons: File System Access API が無いブラウザでは作問できない (今も Chrome / Edge 専用の前提)

#### Option B: メモリ上の作問も残す

- Pros: フォルダを用意せずに試せる
- Cons: 保存のある経路と無い経路の 2 つを保守することになる

### D7. 秘密の置き場と外部での編集

#### Option A: 署名鍵と監督コードは教材フォルダに書かない。鍵は書き出しのときに入力し、監督コードは既存の控えで残す。保存前に外部での変更を検知して上書きしない

- Pros: 教材フォルダを Drive で共有しても秘密が広がらない。共同担当者や同期による変更を黙って消さない
- Cons: 書き出しのたびに鍵を用意する手間が残る

#### Option B: 鍵や監督コードを試験定義に書いておく

- Pros: 書き出しが速い
- Cons: 教材を共有した相手全員に秘密が渡る

#### Option C: フォルダを監視して外部の変更を自動で読み直す

- Pros: 常に最新を表示できる
- Cons: 未保存の編集との衝突の扱いがかえって複雑になる。必要になってから足せる

## Decision

D1〜D7 とも **Option A** を採る (D4 だけ **Option B**)。詳細な形式は `docs/system-spec.md` §4.10 を正本とする。

1. **定義ファイル**: 問題 `*.problem.yaml` (`format: tc-problem/1`)・ケース `*.cases.yaml` (`format: tc-cases/1`)・試験 `*.exam.yaml` (`format: tc-exam/1`)。`format` が未知 (新しい版) のファイルは開かず、上書き保存もしない。書き戻しは変えたキーだけを更新し、コメントと未知のキーを残す
2. **参照パス**: 定義ファイルからの相対パスで、区切りは `/`。絶対パスと、開いたフォルダの外に出る `..` は拒否する
3. **問題の識別子**: 問題定義の `id` を配布物の `problemId` にする。作成時にファイル名の語幹で書き込み、ファイル名を変えても変えない (`problemId` は proof の `templateName` と `problemContentHash` に入るため)
4. **配布物への写像**: `statement` → `statement`、`starter` → `starter` (配布ファイル名は starter の basename)、`public: true` のケース → `examples`。ヒント・解答例・非公開ケース・`title` は配らない。1 つの試験で `id` か配布ファイル名が重複したら書き出さない (授業モードの `ClassProblemStore` は filename で引く)。採用問題の参照ファイルが 1 つでも欠けていたら、問題とパスを示して書き出さない
5. **ケース**: `{ name, stdin, stdout, public?, match? }`。`match` は `trim` (既定) か `exact`
6. **比較と実行**: `trim` は CRLF → LF の後、各行の末尾空白と末尾の空行を取り除いて比べる。`exact` は CRLF → LF だけ。対応言語は C / C++ / Python から始め、1 ケースの実行は 10 秒で打ち切る。C / C++ にも時間の上限を足す。**上限は非対話の実行 (一括検証) だけに掛け、ターミナルからの対話の実行には掛けない** (#802。理由は下の「6 の補足」)。上限はプログラムが動き始めてから数え、ランタイムの読み込みとコンパイルは数えない。結果は proof にも教材フォルダにも記録しない
7. **ヒント**: 配布物に入れない。配ると決めたら別の Issue で `ExamBundleProblem.hints?` を足し、`examples` と同じく 1 件以上のときだけ正準形に入れる
8. **共有**: 「問題を別のフォルダへコピー」で、定義と参照ファイルを相対配置ごと複製する。コピー先に同名のファイルが 1 つでもあれば、何も書かずに中止する。`id` は保つ
9. **フォルダ無しの作問は残さない**。開いたフォルダのハンドルはセッション DB と別の IndexedDB に保存し、再訪時に権限を確かめて再開する
10. **秘密と競合**: 署名鍵と監督コードを教材フォルダに書かない。保存の前に、読み込んだときの `lastModified` と比べ、変わっていれば上書きせずに「読み直す / 上書きする」を選ばせる

**6 の補足 (#802)**: 対話の実行に上限を掛けない理由。C / C++ は Wasmer の pipe で stdin を渡すので、プログラムが入力を待っていることを executor が知る手段が無い (Python の Worker が出す `stdin-request` に当たる合図が無い)。入力待ちの間に時計を止められないため、一律の上限は `scanf` の前で考えている学生の実行を打ち切る。検討した案は、(a) 掛けずに停止ボタンに任せる、(b) 入力待ちも数える長めの上限を掛ける、(c) WASI の `fd_read` を検知して入力待ちの間は数えない (SDK の内部に依存する)。(a) を採る。Python の対話の実行には、入力待ちを数えない上限 (`PYTHON_TIMEOUT_MS`) が既にある。非対話の実行の打ち切りは停止ボタンと同じ経路 (`executor.abort()`) で行い、打ち切った次の実行はランタイム (C / C++ は Wasmer の client、Python は Worker) を作り直す。コンパイルは上限の外なので、コンパイルが終わらない解答 (`<iostream>` を使う C++ = #573) は一括検証を止めうる。**これには自動の上限を足さず、中止ボタンで抜ける** (#799)。コンパイルを含む上限を掛けると、初回のコンパイラの読み込みや遅い端末で、正しい解答を時間切れにしてしまうため。止まっている間、セルは「実行中」のままで、パネルに中止の案内を出す。executor は対話の実行と共有するので、検証とターミナルの実行は画面で排他にする (検証中は「実行」を止め、ターミナルの実行中は検証を始めない。ターミナルの実行は「停止」で止められる = #820)。検証は開いている文書の今の内容 (未保存を含む) を使い、結果はどこにも記録しない。

## Consequences

### Positive

- 教材が手元のファイルとして残り、他のエディタ・バージョン管理・Drive の同期と併用できる
- 予備の問題を同じフォルダに置いたまま、試験ごとに採用と順序を変えられる。同じ問題を複数の試験から参照できる
- 配布物の形と正準化・ハッシュは変わらない (`PROOF_FORMAT_VERSION` も配布物の形式も据え置き)。旧版の editor との互換の注意は増えない
- 公開する入出力例と非公開のテストを 1 つのケースファイルで持ち、一括検証でも同じものを使える

### Negative / Trade-offs

- `/author` は File System Access API が前提になり、Chrome / Edge 以外では作問できない (学生側の editor の前提と同じ)
- 教員が定義ファイルを手で書き換えて YAML を壊すと、そのファイルは開けない。画面は誤りの位置を示すだけで、自動では直さない
- Drive の同期の衝突 (同じファイルを 2 人が同時に変える) は Drive 側の挙動に任せる。複製ファイルができた場合、教員が手で整理する
- ヒントはまだ学生に届かない
- コピーした問題は元の修正を受け取らない

### Follow-ups / 残課題

- 実装は済んだ: #794 (定義ファイルの読み書き) / #795 (フォルダの読み書きと再開) / #796 (作問画面) / #797 (試験定義と書き出し) / #798 (ケースの編集画面) / #799・#802 (一括検証) / #800・#817 (問題のコピー) / #820 (`/author` の停止ボタン)
- 実フォルダ・本物のピッカー・権限の再要求・Drive の同期フォルダでの手動確認 (#825)。自動テストは OPFS (権限が常に許可済み) で通しているので、ここは人が確かめる
- `<iostream>` を使う C++ のコンパイルが終わらない問題そのもの (#573)。一括検証では中止で抜ける (#799)
- ヒントの配布と見せ方 (使ってから別の Issue で決める)
- 提出物の一括採点 (ADR-0048 の段階 2 のうち、学生の提出物を再実行する部分) は別に扱う。比較規則はこの ADR のものを使う
- 1 つの解答が複数のソースからなる場合は #713 / #715 で決める
