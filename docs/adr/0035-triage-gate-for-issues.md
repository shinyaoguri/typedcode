# ADR-0035: 着手できる Issue を、メンテナが `verify: triaged` を付けたものに限る

- **Status**: Accepted
- **Date**: 2026-11-01
- **Deciders**: @shinyaoguri
- **PR / Commit**: (#377。追跡 Issue #372)

## Context

起票の速さに消化が追いついていない。2026-10-31 のレビュー (#334) では、2026-08-01 以降の起票 75 件に対して close 40 件で、P1 の 6 件が 7 週間 open のまま残っていた。起票の多くはレビュー由来で、エージェントが書いている。

着手の条件は決まっていなかった。そのため、受け入れ条件が書かれた時点のまま古くなった Issue にも、そのまま着手できた。また、受け入れ条件を書けない (仕様や方針の選択が要る) Issue と、すぐ直せる Issue が同じ一覧に混ざり、どれが「やると決まったもの」なのかが外から読めなかった。

同じ問題に、姉妹プロジェクトの mokume は「着手は `verify: triaged` の付いた Issue だけ」「印を押すのは受け入れ条件を知る起票者」で答えている (#372 で比べた)。typedcode は個人アカウントのリポジトリなので Issue Type は使えないが、ラベルによるゲートはそのまま使える。

## Considered Options

### Option A: ゲートを置かない (現状)
- Pros: 手間が増えない。誰でもすぐ着手できる
- Cons: 「起票した」と「やると決めた」が区別されない。古くなった受け入れ条件のまま着手され、判断の要る Issue をエージェントが勝手に決めて進められる

### Option B: ゲートを置き、エージェントも印を付けてよい
- Pros: 人の手間がほとんど増えない
- Cons: 受け入れ条件を書いた者が自分で印を押すので、中身を見ずに印が付く方向へ倒れる。「やると決める」判断が人に残らず、A と実質同じになる

### Option C: ゲートを置き、印は原則メンテナだけが付ける (採用)
- Pros: 「やると決める」判断が人に残る。印を押す場所が端末のプラン承認から GitHub のラベル 1 つへ移り、材料 (受け入れ条件の調査) は人が居ない間にエージェントが溜められる
- Cons: 印を押す手間が増える。印が付くまで着手できる Issue が無くなる

## Decision

C を採る。着手できるのは `verify: triaged` の付いた Issue だけで、印はメンテナが付ける。例外は、エージェントが作業中に踏んでその場で起票し、受け入れ条件を自分で書けた Issue だけ (その PR の文脈で根と範囲を確かめているため)。あわせて、着手時に各受け入れ条件を現行コードと突き合わせ、「まだ有効 / 既に満たされている / 差し替えが要る」をプランに書く。印が付いた後も Issue は書かれた時点の話しかしていないので、着手の瞬間に確かめ直す。

## Consequences

### Positive
- open な Issue のうち「やると決まったもの」がラベル 1 つで一覧できる
- 受け入れ条件を書けない Issue が、印の無いまま判断待ちとして残り、混ざらない
- 古い受け入れ条件のまま実装する事故 (既に直っている・行番号が動いている) を着手時に止められる

### Negative / Trade-offs
- 印を押すメンテナの手間が増える
- 導入直後は印の付いた Issue が無いので、着手できるものが無い。既に `status: in progress` の Issue は対象外として続ける

### Follow-ups / 残課題
- #378: 種類ラベルを `type:*` に置き換える (Issue Type の代替)
- #379: 未トリアージの Issue を調べて受け入れ条件を書くスキル (印は付けない) と、着手候補を出すスクリプトをリポジトリ内に置き、ゲートを機械側から支える
