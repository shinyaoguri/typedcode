# ADR-0034: 機能追加時の手動動作確認を自動テストで置き換える

- **Status**: Accepted
- **Date**: 2026-10-31
- **Deciders**: @shinyaoguri
- **PR / Commit**: (追跡 Issue #346 の PR 1「テスト基盤の土台」)

## Context

機能を足すたびに、エディタと検証画面を手で開いて動作を確かめている。手動確認は次の理由で回らなくなっている:

- **網羅されない**: モード (通常 / 授業 / 課題 / 試験)・ロケール・検証モードの組み合わせが増え、毎回すべてを手で踏むことはできない。踏まなかった組み合わせで退行が出る
- **記録に残らない**: 何を確認したかが PR に残らず、同じ確認を次の PR でまたやる。エージェントが実装する場合はなおさら「確認した」の中身が検証できない
- **CI 緑が信用されない**: ユニットテストと E2E ([ADR-0033](0033-e2e-round-trip-harness-as-deploy-gate.md)) が緑でも手で確認し直しているのは、緑が「動く」を意味していないから。テストを足す仕組みも、テストが減っていないことを検出する仕組みも無かった (verify-cli はテストファイルを型検査からも外していた: #336)

目標は「**CI が緑なら手動確認は不要**」と言える状態。そのためには (1) 何をオラクルにするか、(2) UI と見た目をどう機械検査するか、(3) テストが増え続け減らないことをどう強制するか、を決める必要がある。

制約:

- 暗号的な検証 (verify-cli の結論) は既に E2E のオラクルとして機能している (ADR-0033)。これを崩さない
- UI の文言は i18n (ja / en) で変わる。翻訳テキストを assert に使うと文言修正でテストが壊れる
- CI は ubuntu、開発機は macOS。フォント・アンチエイリアスが OS で違う
- 開発の相当部分をエージェントが担う。規約は文書だけでなく CI で強制しないと守られない

## Considered Options

### Option A: 手動確認を続け、PR テンプレートのチェックリストで補う

- Pros: 追加の仕組みが要らない。人間の目で見た目の違和感も拾える
- Cons: 上記の網羅・記録・信頼の問題がそのまま残る。チェックリストは押すだけの確認になり、実際に何を踏んだかは検証できない

### Option B: 画素比較 (visual regression / スクリーンショット差分) で UI を検査する

- Pros: 見た目の退行を広く拾える。テストを書く手間が小さい
- Cons: OS・フォント・ブラウザ更新で基準画像がずれ、CI (ubuntu) と手元 (macOS) で結果が一致しない。基準画像の更新・レビュー・保管の運用コストが恒常的にかかり、差分が出るたびに「意図した変更か」を人が判定することになる (= 手動確認が形を変えて残る)。flaky な赤はゲートの信頼を崩す

### Option C: 翻訳テキスト・CSS セレクタ・見た目に依存した DOM アサーション

- Pros: 一般的で書きやすい
- Cons: 文言修正・ロケール・デザイン変更でテストが壊れる。ADR-0033 が UI アサーション中心の E2E を退けた理由 (flaky で信号が信用されなくなる) がそのまま当てはまる

### Option D: 暗号的成果物を第一のオラクルに保ち、UI は data-* 属性の状態契約で、見た目は DOM / 状態 / a11y / レイアウト不変条件で機械検査する。テスト追加はゲートとカバレッジのラチェットで強制する

- Pros: 文言・OS・デザインに依存しない安定した信号になる。状態契約は実装とテストの間の明示的なインターフェースとして残り、エージェントも従える。「テストが増え続け、減らない」を CI が判定する
- Cons: 状態を data-* で出す実装コストがかかる。画素レベルの見た目崩れ (色・余白の微妙なずれ) は検出しない。ゲートには逃げ道が要り、その乱用は人のレビューで見る

### Option E: カバレッジ閾値を固定の目標値 (例: 80%) で課す

- Pros: 目標が分かりやすい
- Cons: editor / verify のように現状が低いパッケージでは即座に全 PR が落ちる。逆に現状が目標より高いパッケージでは、目標まで下がっても検出しない。「減らない」を強制できない

## Decision

**Option D** を採る (カバレッジは Option E の固定値ではなく、実測値の床を上げていくラチェットにする)。具体的には:

1. **判定のオラクルは暗号的成果物を軸に維持する**。編集 → export → verify-cli の結論 (exit code / `--analysis-json`) が第一のオラクルで、改竄で落ちる負のオラクルと対にする (ADR-0033 を踏襲)
2. **UI は data-* 属性の状態契約で E2E から検査する**。画面の状態 (検証結果・保証層の値・モード・進行段階など) は、生の enum 値・状態を `data-*` 属性で DOM に出し、E2E はそれを読む。翻訳テキスト・CSS クラス・見た目には依存しない。属性名と値域は検査対象の契約として扱い、変えるときはテストと同時に変える
3. **見た目は画素比較しない**。代わりに DOM 構造・状態・アクセシビリティ (axe による自動検査)・レイアウト不変条件 (要素が viewport からはみ出さない・重ならない・可視である等) を機械検査する。画素比較は OS 差と基準画像の運用コストで不採用
4. **「テストが増え続け、減らない」を CI で強制する**:
   - **完了の定義 (Definition of Done)** を CONTRIBUTING.md に置く (UI の振る舞いを変えたら E2E と data-* フック、ロジックはユニットテスト、バグ修正は先に赤いテスト)
   - **テスト必須ゲート** (`pr-checks.yml` の `require-tests`): 実装 (`packages/*/src`) を変えた PR にテストの変更が無ければ落とす。docs / ci / chore 型・依存更新は対象外。テストが本当に不要な PR はラベル `no-test-needed` + PR 本文の `## テスト不要の理由` で通す
   - **カバレッジのラチェット**: 全パッケージで `coverage.thresholds` を実測値の切り捨てで固定し、下回ると CI の test job が落ちる。上げたら `npm run coverage:ratchet` で床を引き上げる (普段のテストでは設定を書き換えない)
   - テストファイル自体も型検査に含める (#336)
5. **既知バグは失敗する再現を先に置く**。直す前のバグは E2E なら `test.fixme('#N ...')` で再現を置き (Issue 番号をタイトルに含める)、修正 PR で `fixme` を外して緑にする。直したことがテストの状態変化として PR に残る

## Consequences

### Positive

- 「CI が緑 = 手動確認不要」を目指せる前提が揃う。何を確認したかが PR のテスト差分として残る
- 文言・ロケール・OS に依存しない E2E になり、flaky な赤でゲートの信頼が崩れにくい
- data-* の状態契約は a11y や i18n の検査 (後続 PR) にもそのまま使える
- カバレッジは下がれば落ちるので、テストの削除や未テストのコード追加が黙って通らない

### Negative / Trade-offs

- UI に状態を出す data-* 属性の実装と維持のコストがかかる (本番 DOM にも出る。値は生の enum で、個人情報は出さない)
- 画素レベルの見た目崩れは検出しない。見た目の最終確認が必要な変更は、PR の「自動化できず手動で確認したこと」欄に理由とともに残す
- テスト必須ゲートはファイル単位の粗い判定で、テストの中身の妥当性までは見ない (レビューで見る)。`no-test-needed` の乱用もレビューで見る
- カバレッジの床は実測値の切り捨てなので、1% 未満の低下は検出しない

### Follow-ups / 残課題

- 追跡 Issue #346 の後続 PR: verify の data-* 状態契約、モード別の E2E、障害注入、a11y / i18n の機械検査
- ラベル `no-test-needed` の作成と、`require-tests` を main ruleset の required status check に加えること
- editor / verify のカバレッジは現状低い。床は上がった分だけラチェットで引き上げる
