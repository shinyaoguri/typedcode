# ADR-0053: 仕様別の検証器を維持し、新仕様の識別子を暗号的に束縛する

- **Status**: Accepted (方針決定済み、実装は #809・#810。現行形式・検証結果はこの文書 PR では変えない)
- **Date**: 2026-11-18
- **Deciders**: @shinyaoguri
- **PR / Commit**: #805 を閉じる文書 PR

**要約**: 新しい書き手が破壊的な仕様変更を行っても、過去のファイルを元の仕様で検証する。仕様の識別・暗号整合性・信頼・受理を分け、未知形式を推測で検証しない。
**人が判断すること**: なし。新形式の正確な計算式・割当値は #810 の仕様と固定ベクタで確定する。ここでは維持すべき契約を決める。

## Context

メンテナは利用者がいない現時点での破壊的変更を許容する一方、互換性が失われた旧仕様でも、版に応じて適切に検証できることを求めた (#804)。旧アプリがすべての新ファイルを読めるという相互互換性と、現在の検証器が旧ファイルを読める長期互換性は別の要件である。

現行 `classifyProofVersion` は既知 major 内を広く受け入れ、未知 major は警告に留める。`verifyProofFile` のコメントは `proof.version` が `typingProofHash` の入力でないことを明記する。exam の manifest は formatVersion を署名 core に含むが、proof 全体に同じ保護があるわけではない。

既存の凍結 proof (#581) は、書き手と読み手の共通処理を同時変更すると最新版同士のテストだけでは旧ファイルの破損を検出できない、という実害を固定している。この資産を仕様別の検証に引き継ぐ。

ADR-0051 の「作問改修では配布形式を変えない」という範囲は維持する。新しい配布仕様への更新は #810 の別変更として行い、#792 系の既存 Issue の条件をこの ADR によって暗黙に差し替えない。

## Considered Options

| 案 | 利点 | 欠点 |
|---|---|---|
| 全アプリを同じ版で一括公開する | 最新同士の整合を取りやすい | 独立公開を妨げ、保存済みファイルや旧ブラウザを解決しない |
| 旧ファイルを新形式へ変換してから検証する | 検証経路を一つにできる | 元の署名・正準化・計算の意味を変えてしまう |
| 現在の検証器に仕様別の処理を同梱する | 原本と規則を保ち、外部 SDK とも共有できる | 旧仕様の処理と fixture の維持が必要 |
| 過去のアプリ全体を保存して起動する | 当時の実装を再現しやすい | 古い UI・依存・脆弱性を保持し、外部利用と保守が重い |

## Decision

仕様別の処理を現在の検証器へ同梱する。旧ファイルを原本のまま検証し、結果だけを共通モデルへ変換する。旧アプリとの相互互換性は初回再設計の制約にしない。

### 1. 版の責務

| 識別情報 | 役割 |
|---|---|
| アプリ/SDK の版と commit SHA | 実装とリリースの追跡。SDK API は SemVer で管理 |
| ファイルの種類と仕様版 | 構造、意味、正準化、暗号計算、再生規則の選択 |
| 保存する検証結果・イベントビューの schema | 外部アプリが派生データを読む契約 |
| trust snapshot / policy の識別子 | 何を信頼し、どの条件で受理したかの追跡 |

新規の形式は `kind` と整数 `specVersion` で明示する。具体的な kind 文字列と割当番号は #810 で規定し、実装の定数を正本とする。既存の `version` / `formatVersion` / `schema` は legacy adapter が元の定義で読む。proof、問題パッケージ、署名 envelope は種類ごとに版管理し、参照できる組み合わせを仕様に記載する。アプリの公開回数に合わせてファイルの版を上げない。

検証の意味・計算・既定値・再生規則を変えるときは新仕様を割り当てる。仕様どおりの動作に直す実装修正と UI 改修は仕様版を変えない。既存フィールドを別用途へ流用しない。省略/未知フィールドを許す範囲と署名対象は版ごとに明記し、「任意フィールド追加だから安全」とは判定しない。

### 2. exact dispatch と legacy

1. 入力サイズ・構造・種類・版を境界で検査する。
2. 静的な対応 registry から検証器を一つ選ぶ。実装していない版を大小関係や同じ major という理由だけで対応済みにしない。
3. その仕様の parser、canonicalizer、root/hash、PoSW、署名・内容照合を原本に適用する。
4. 結果を共通モデルへ写し、信頼と受理を評価する。

未登録の種類/版は `unsupported`、識別子や構造が不正なら malformed、既知形式で計算が一致しなければ検証失敗と区別する。検証失敗後に旧版へ fallback しない。入力内の URL から検証コード・信頼鍵を取得しない。

legacy の対応一覧と識別規則は #809 で現行コード・既存 fixture に基づき確定する。旧 root 束縛やパッケージの方式も明示的に扱う。旧仕様に版の暗号的束縛がなければ、その保証を持つと説明しない。新仕様の安全性を旧ファイルへ後付けできない。

### 3. 新仕様では種類・版を証拠へ束縛する

新仕様の kind/版は、ドメイン分離された正準な起点と、そこからのハッシュチェーン・署名付き証拠に結び付ける。author の package 署名、editor の root、workers の token/checkpoint の対象を式と固定ベクタで確認する。版だけの書換え、別種類の署名の流用、旧新の envelope の混在が成功しないようにする。

正準化・暗号 suite と許すパラメータの範囲は仕様が決める。ファイルが任意の algorithm を指定して検証処理を選ばせる設計にはしない。安定した primitive は共有してよいが、仕様固有の canonicalizer 等を「最新版」にすり替えない。

ハッシュだけの未署名ログは再計算可能であり、版の束縛だけで真正性は得られない。古い形式として新しく作ったファイルを、旧仕様対応を理由に現在の提出条件で自動受理しない。受理方針で許す仕様と必要な信頼証拠を選ぶ。旧形式の受理可否と旧形式を解析・検証できる能力は別である。

### 4. 検証結果と信頼・受理

結果は少なくとも次を別の軸として持つ (正確な公開型は ADR-0054)。

- 仕様への対応状況。
- チェーン、PoSW、署名、内容、問題束縛など各検査の成功/失敗/未実施/対象外。
- 必要資料の欠落・省略と、それによる保証範囲。fast の PoSW 省略を full 成功と同じにしない。
- 鍵の信頼・失効・根拠となる時刻・legacy/暗号方式の制限。
- 現在の受理方針への適合。

「当時の仕様で計算が合う」と「現在も信頼できる」は別である。鍵の失効・漏えい・暗号上の知見を、古い検証コードに合わせて無視しない。評価時刻・trust snapshot・policy は明示入力とし、その識別情報を結果へ残す。署名者の自己申告日時だけで、漏えい前に作られたと証明しない。鍵同梱は署名の数学的照合を助けても、信頼の根にはならない。

旧検証器に不具合や脆弱性があれば修正する。維持するのは仕様の意味であり、過去の誤判定ではない。判定変更の理由と SDK/結果の版を記録する。歴史的な鍵 snapshot での評価を行う場合は、現在の信頼評価と区別して表示する。

### 5. 長期テストと公開順序

各仕様に、仕様書、検証実装、正常/改変/境界の固定ベクタをそろえる。既存の凍結ファイルは再生成せず、新しい形式は別ファイルとして追加する。新しい書き手と読み手だけを同時に試して完了にしない。旧仕様の再生も固定データで確かめる。

利用者がいない初回は破壊的に切り替えてよい。利用開始後の形式変更は、読み手が旧新を扱える準備版を先に公開し、次に新形式の出力を有効にする。新形式の出力後は準備版より前へ戻さない。ブラウザに旧アプリが残ることと、保存済みファイルの長期サポートを区別し、試験中の強制 reload に依存しない。全過去アプリ版の総当たりや常時オンラインの互換性交渉サービスは作らない。

## Consequences

### Positive

- 新仕様への改善と、旧提出物の再検証を両立できる。
- 未対応を改ざんや成功に混ぜず、外部サービスも検証範囲を扱える。
- 仕様を固定ベクタとともに公開でき、他言語実装の基礎にもなる。

### Negative / Trade-offs

- 支持する旧仕様の reader と fixture を維持する費用がある。
- 旧形式の保証限界は解消できず、現在の受理条件で認めない場合がある。
- 新仕様の正確な計算式と token/checkpoint の整合は #810 で実装・負の対照を伴って確定する。本 ADR だけで新形式を出力してよいとはしない。
