# ADR-0055: リリースを main → beta → 正式版 (年 2 回) の 3 チャンネルにし、版を暦の形でタグから自動採番する

- **Status**: Accepted (#842・#843・#844 で実装済み。残りは beta 環境の #845。[ADR-0028](0028-tag-based-github-flow.md) のうち「`v*` タグならどれでも production」「緊急修正は main へ fix → 即パッチタグ」「`release/*` の廃止」を置換。決定 2・5・6 は #844 の実装時に修正した (2026-11-20))
- **Date**: 2026-11-20
- **Deciders**: @shinyaoguri
- **PR / Commit**: (#841 を閉じる PR)

## Context

ADR-0028 は main 1 本 + `v*` タグで production へ出す形を決めた。タグを打つまでは人の手で、手順は「版の bump の PR → `CHANGELOG.md` の `[Unreleased]` を切る → `gh release create`」である ([CONTRIBUTING.md](../../CONTRIBUTING.md)「リリース」)。この形に 2 つの問題が出た。

1. **打ち忘れが繰り返す**: リリースの停滞は #85 と #332 で 2 回起き、自動検知 (#410) を足した。その後も v1.2.0 から 4 日で feat / fix が 40 件たまり、上限を「最新タグから 7 日以内」に縮めた (#657)。人が打つ限り、規則と検知で追いかけることになる。
2. **授業の期間と両立しない**: TypedCode は授業・試験で使う。受講者が使っている最中、とくに試験中に production の挙動が変わるのは困る。7 日ごとに出す規則は、利用者が付いた後は学期と必ず重なる。凍結期間を設けるかは #662 で未決のままだった。

メンテナは 2026-11-20 に次を決めた。

- 正式なリリースは年 2 回、授業の無い 2 月と 8 月に行う。
- それ以外の時期の変更は、beta 版として版を積み重ねる。
- 版の番号は、別リポジトリ (mokume) と同じく、リリースのたびに自動で付ける。ただし mokume と違い動いているサービスなので、merge のたびに production へ出ることは避ける。

判断の前提になる制約:

- main は PR 必須で、必須チェック (test / check / e2e) がある。GitHub Actions の既定のトークンで作った PR と push したタグは、他のワークフローを起こさない (再帰を防ぐ GitHub の仕様)。版を書き換える PR を自動で作っても、必須チェックが走らない。
- staging は Turnstile の公開テストキーで動く ([ADR-0049](0049-staging-turnstile-testing-keys.md))。session/start を事実上誰でも通せるので、実利用の場にはできない。
- production の配信は GitHub Environment の承認ゲートを通る。ruleset は `v*` タグの削除と更新を禁じている (作成は許す)。
- 未マージの設計 (PR #814 の ADR-0052) が、タグを検証済みスナップショットとし、公開を「アプリ + 環境」の指定に分けることを決めている。

## Considered Options

### 1. production へ出す契機

| 案 | 利点 | 欠点 |
|---|---|---|
| A: 現状 (7 日以内に人がタグを打つ) | 変更なし。1 回の差分が小さい | 学期中に production が変わる。打ち忘れを規則と検知で追い続ける |
| B: merge ごと・日次で自動に production へ (mokume と同じ) | 手作業が無い | 学期中・試験中に挙動が変わる。承認ゲートを毎回押すか、外すことになる |
| C: 凍結期間だけ止め、その外では 7 日ごと (#662 の案) | 差分が小さいまま試験を避けられる | 授業・試験の日程を誰かが登録し続ける必要がある。授業期間の全体は守れない |
| D: 機能フラグで隠して production へ出し続ける | ブランチが 1 本で済む | フラグの裏でも記録・検証の経路は動く。証明の挙動を変えないことをフラグごとに保証できない |
| **E: 正式版は年 2 回、それ以外は beta 版として積む** | 学期中の production が変わらない。日程の登録が要らない | 半年分が一度に出る。学期中の緊急修正に別の経路が要る |

### 2. 版の形

| 案 | 利点 | 欠点 |
|---|---|---|
| SemVer のまま、beta は `v1.5.0-beta.N` | 今のタグと連続する | beta が向かう正式版を先に決める必要がある。途中で破壊的変更が入ると `v2.0.0-beta.1` へ切り替わる。番号から時期が読めない |
| **暦で付ける (`v2027.2.0-beta.N` → `v2027.2.0`)** | 向かう版が日付から決まる。教員が「2027 年 2 月の版」と読める | 今の `v1.4.0` から番号が飛ぶ。番号は互換性を表さない |

互換性は、アプリの版ではなく `PROOF_FORMAT_VERSION` などファイル形式の版が既に表している (`packages/shared/src/version.ts`)。

### 3. 版の正本

| 案 | 利点 | 欠点 |
|---|---|---|
| ルートの `package.json` と `CHANGELOG.md` を、リリースのたびに自動の PR で書き換える | 今の正本 (#658) のまま | 既定のトークンの PR は必須チェックを起こさない。迂回 (別のトークンや App) はリリースのたびに壊れる場所を増やす |
| **タグと GitHub Releases だけ。リリースはファイルを変えない** | 自動採番の妨げが無い。二重管理が無い | リポジトリの中だけでは版と履歴が読めない |

### 4. beta の配信先と頻度

| 案 | 利点 | 欠点 |
|---|---|---|
| タグと Release だけにし、staging を beta と見なす | 環境が増えない | staging はテストキーなので、beta を実際に使って試す人がいない |
| **専用の beta 環境 (本物の Turnstile と専用の署名鍵)** | 学期中も新しい版を実利用で試せる | Worker・KV・署名鍵・Turnstile・ドメインがもう一組要る |

頻度は、日次 (採用)・週次・手で起こすときだけ、を比べた。日次は 1 回の差分が最も小さく、壊れたときに原因を追いやすい。手で起こす形は、打ち忘れという元の問題を beta に持ち込む。

### 5. 学期中の緊急修正の経路

| 案 | 利点 | 欠点 |
|---|---|---|
| main の先端から出す (ADR-0028 のまま) | ブランチが 1 本 | main には半年分の未リリースの変更があり、fix だけを出せない |
| **正式版のタグから `release/YYYY.M` を切り、fix を cherry-pick する** | fix だけを出せる | ADR-0028 が消した「2 か所への反映」が、緊急修正のときだけ戻る |

配信の定義をどこから取るか (#844 で追記):

| 案 | 利点 | 欠点 |
|---|---|---|
| main の定義で配信する (main の run の中でタグを打ち、そのコミットを checkout して出す) | 配信のゲートが常に main の最新 | main の構成が変わった後 (#808 など) に、旧構成の正式版の patch を出せない |
| **タグの ref の定義で配信する (`deploy.yml` の `workflow_dispatch` をタグの ref で起こす)** | `release/*` が自分のコードに合う定義を持つ | 配信の経路が壊れていたら、同じ版では直せない (直した定義を持つ次の版で前へ進める) |

## Decision

案 E を採る。版は暦の形でタグから自動採番し、正本はタグと GitHub Releases に置く。beta は専用環境へ日次で出す。

### 1. チャンネル

| チャンネル | 契機 | 版 | 配信先 | 承認 |
|---|---|---|---|---|
| main | merge ごと | 付けない | staging | なし |
| beta | 日次 (出すものがある日だけ)。手動でも起こせる | `vYYYY.M.0-beta.N` | beta 環境 | なし |
| 正式版 | 2 月と 8 月に、人が起こす | `vYYYY.M.0` | production | Environment の承認 |
| patch | 学期中の緊急修正。人が起こす | `vYYYY.M.P` (P ≥ 1) | production | Environment の承認 |

main 1 本・PR は squash・main push で staging、という ADR-0028 の形は変えない。

### 2. 版の形と決め方

- 形は `年.月.patch`。月は 2 か 8 で、先頭に 0 を付けない (`2027.2.0`。SemVer の文法としても有効)。
- **beta が向かうサイクル** (`YYYY.M`) は、その日以降で最初に来るリリース月 (月末まで含む)。その月の正式版が既に出ていれば、次のサイクル。
- beta の `N` は、同じサイクルの beta タグの最大 + 1。数として比べる。
- **正式版の名前は、昇格させる beta タグから `-beta.N` を除いたもの**。日付からは決めない。

| 日付 | 既にあるタグ | 次の beta |
|---|---|---|
| 2026-11-20 | `v1.4.0` だけ | `v2027.2.0-beta.1` |
| 2027-02-10 | `v2027.2.0` が無い | `v2027.2.0-beta.<次>` |
| 2027-02-15 | `v2027.2.0` がある | `v2027.8.0-beta.1` |
| 2027-03-01 | `v2027.2.0` が無い | `v2027.8.0-beta.1` |

リリース月に正式版を出さなかったサイクルは欠番になる (最後の行)。SemVer の `v1.x` 系は `v1.5.x` が最後になる (新しい経路の通し稽古で `v1.5.0` と `v1.5.1` を出す。決定 6)。

### 3. 版の正本と変更履歴

- 版の正本はタグと GitHub Releases。**リリースはリポジトリのファイルを 1 つも変えない**。
- About に出る版は、ビルドに渡したタグ名から決める。タグでないビルド (staging・PR プレビュー・手元) は版を名乗らず、コミットで区別する。ルートの `package.json` の `version` は正本から外す。
- 変更履歴は、PR ごとに 1 ファイル足す断片 (`changelog.d/`) に書く。Release のノートは、前回のタグ以降に足された断片から組む。`CHANGELOG.md` は `v1.4.0` までの記録として残し、書き足さない。
- 断片を持たない fix / feat は、コミット件名をノートに載せる。断片を必須にする PR ゲートは足さない。

### 4. beta 版を出す条件

- 最新のタグ以降に fix / feat のコミットが 1 件以上あること。無い日は見送る。
- タグを打つのは、main のコミットのうち、staging への配信と実 URL の E2E まで通った最新のもの。main の先端とは限らない。
- 既存の nightly のゲート (main の最新の完了 nightly が success) を通す。
- Release は prerelease として作り、Latest にしない。
- beta 形のタグでは production へ配信しない。

### 5. 正式版は beta の昇格

- 人が beta タグを指定して起こす。その beta と同じコミットに正式版のタグを打つ。main の先端には打たない。
- 既存のゲート (タグの ref での test / check / e2e の再実行・nightly のゲート・Environment の承認・タグは消さず付け替えない) はすべて残す。
- ノートは、前回の正式版以降の全断片。
- 2 月・8 月という時期は規約で守る。それ以外の月の昇格を止める検査は足さない (昇格は人が起こし、承認ゲートがある)。
- ただし、**サイクルの月がまだ来ていない beta の昇格は拒否する** (#844)。止めるのは時期ではなく版の名前のずれ: 3 月に `v2027.8.0-beta.N` を昇格すると `v2027.8.0` が 3 月に出て、以後の beta は次のサイクルへ進み、8 月の正式版が `v2028.2.0` を名乗る。2 月の正式版が 3 月にずれたら、2 月の最後の beta を昇格する。
- production の配信は、打ったタグの ref を指定した `deploy.yml` の `workflow_dispatch` で起こす (タグの push では起こさない)。`workflow_dispatch` は指定した ref にある定義で走るので、配信の定義はタグのコミットのものになる。`release/*` は自分のコードに合う定義を持ち、main の構成が変わった後も古い正式版の patch を出せる。

### 6. 学期中の patch

- **patch にしてよいのは次の 3 つだけ**: 本番に効くセキュリティ修正・データを失う不具合・授業や試験が続けられない不具合。機能の追加と見た目の変更は次の正式版まで待つ。
- 本番に効くセキュリティ修正を main に入れたら 7 日以内に patch を出す、という今の規則は維持する。
- 正式版 `vA.B.0` から `release/A.B` を切る。切るのは最初の patch が要るときでよい。
- **fix は先に main へ入れ、その cherry-pick を `release/A.B` 宛ての PR で入れる**。`release/A.B` にだけある修正を作らない。
- patch のタグは `release/A.B` の先端に打つ。production の配信は「`.0` は main の祖先、patch は対応する `release/A.B` の祖先で、かつ `vA.B.0` の子孫」を検証する。
- 新しい経路を本番で一度通すため、この実装 (#844) の後に `v1.5.0` を main に手で打ち、続けて `release/1.5` から `v1.5.1` を出す。以後、初回の正式版までの production は `v1.5.x` で、その間の緊急修正は同じ規則で `release/1.5` から出す (`release/1.4` は作らない)。

### 7. beta 環境

- 本物の Turnstile と、beta 専用の署名鍵・KV・Worker を持つ。テストキーの結果を通すのは staging だけ、という ADR-0049 の決定は変えない。
- beta 版ができるたびに、承認なしで配信する。
- origin が production と別なので、保存データは分かれる。beta の editor は production より新しい形式の proof を出しうるので、beta で作った proof は beta の verify で検証する。
- beta で作った proof を採点で受け入れるかは、ここでは決めない (受理ポリシーは採点者のもの。[ADR-0043](0043-acceptance-policy-separated-from-integrity.md))。
- 足すのは #808 (アプリ別の origin と Pages) の後にする。先に足すと、#808 で beta の配信先を分け直すことになる。

### 8. やめるもの

- 版の bump の PR と、`CHANGELOG.md` の `[Unreleased]` を切る手順。
- 正式版を `gh release create` で手で出す手順。
- 「最新タグから 7 日以内にリリースする」規則と、停滞の自動検知 (#657・#410)。日次で beta が出るので、停滞は起きない。
- 授業・試験の期間の凍結を別に決めること (#662)。学期中に production へ入るのは patch だけになる。

### 9. 他の ADR との関係

- **ADR-0028**: main 1 本・staging・タグを消さず付け替えないこと・タグの ref での再検証・承認ゲートは維持する。置き換えるのは、`v*` タグならどれでも production へ出ること (正式版と patch だけにする)、緊急修正を main の先端から出すこと、`release/*` を持たないこと (緊急修正のときだけ持つ)、タグを人が `gh release create` で打つこと、の 4 点。
- **ADR-0052 (PR #814、未マージ)**: あちらは公開の単位 (アプリ + 環境) を決める。この ADR はタグの付け方と、環境に beta を足すことを決める。production の配信を作り替える点が重なるので、後から実装する側が先に入った形へ合わせる。

## Consequences

### Positive

- 学期中に production の挙動が変わらない。授業・試験の日程を登録する仕組みが要らない。
- 版を上げる手作業と、打ち忘れを追いかける規則・検知が無くなる。
- 並行する PR が `CHANGELOG.md` の同じ節を書き換えて衝突することが無くなる。
- 版の番号から、いつの版か・正式版か beta かが読める。

### Negative / Trade-offs

- **半年分の差分が一度に production へ出る**。#657 が守ろうとした「壊れたときに原因を追える大きさ」は、production については手放し、beta の日次の粒度で担保する。beta を実際に使う人が少なければ、この担保は弱い。
- **緊急修正のときだけ、2 か所への反映が戻る** (main と `release/A.B`)。ADR-0026 で払っていた費用の一部を、頻度を下げて払い直す。
- `release/A.B` 宛ての PR (backport) は、main 宛てと同じ検査を通す。test / check / e2e は `release/**` 宛ての PR と push でも走る (staging へは出さない)。`Closes #N` の紐づけは既定ブランチ宛ての PR にしか作られないので、backport の PR は本文に元の fix の PR を書き、ラベル `no-issue` で `require-issue` を通す (#844)。
- リポジトリの中だけでは版と変更履歴が読めない。GitHub の外へ持ち出した複製では、タグは残るが Release のノートは残らない。
- 版の番号が `v1.5.x` から `v2027.2.0` へ飛ぶ。番号は互換性を表さない。
- beta 環境の維持 (署名鍵・Turnstile・KV・ドメインがもう一組) が増える。
- 断片を書き忘れた変更は、コミット件名のままノートに載る。

- #845 (残り): beta 環境を足す (#808 の後)。
