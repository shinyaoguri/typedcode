# packages/shared — モジュール一覧

どのモジュールが何を持つか。[AGENTS.md](../AGENTS.md) から移した表で、守るべき規則は AGENTS.md の不変条件と [invariants.md](invariants.md) にある。パスは `packages/shared/src/` から見たもの。

| モジュール | 役割 |
|---|---|
| `typingProof/TypingProof.ts` | ハッシュチェーンのファサード。エディタが使う |
| `typingProof/HashChainManager.ts` | SHA-256 計算とチェーン状態管理 |
| `typingProof/PoswManager.ts` | PoSW 計算 (Web Worker 経由)。Worker 自体の故障 (`onerror`、または生成直後から `observePoswWorkerFailure` で観測した attach 前の故障) を受けた個体は terminate して捨て、作り直さずにメインスレッドのフォールバックへ直行する (#701。個別要求の期限切れは 1 件だけフォールバックし、Worker は使い続ける)。Worker を作る側は `observePoswWorkerFailure` を `new Worker` と同じ同期区間で呼ぶ (editor は `workers/createPoswWorker.ts`) |
| `typingProof/CheckpointManager.ts` | ハイブリッドトリガ (N events OR T ms) で cp 作成 |
| `typingProof/InputTypeValidator.ts` | 許可/禁止 InputType の判定 |
| `typingProof/StatisticsCalculator.ts` | 統計計算 |
| `signedCheckpoints.ts` | 署名済み cp の payload 構築・検証・冪等判定。anchoring 密度 (ADR-0016) の計量も (gate は `acceptancePolicy.ts`)。post-hoc と疎は**ハッシュ対象の `event.timestamp` と `serverTimestamp` の照合**で測り、申告値の `clientTimestamp` を判定に使わない (#320。`clientSpanMs` / `ratio` は表示用)。post-hoc の基点に token の `issuedAt` を使うのは root が検証済みのときだけで、`verifyProofSignedCheckpoints` は `sessionAnchorIssuedAt` を必須で受ける |
| `acceptancePolicy.ts` | 受理ポリシー (ADR-0043)。`evaluateAcceptancePolicy` が root / 密度 / 署名 cp の存在 / 最終署名の 4 つの opt-in 要件から違反 (列挙型の code) を列挙する純関数。`verifyProofFile` が `integrityValid` (ポリシー無しの結論) と `policy: { applied, evaluated, violations }` を分けて返し、`valid = integrityValid && violations が空`。**整合性が落ちたら評価しない** (`evaluated: false`)。`integrityValid` は `assurance.integrity` や Tier A バンドルの `integrityValid` とは別の値。密度 gate はここにあり、`verifySignedCheckpoints` は密度で `valid` を落とさない |
| `sessionStartToken.ts` | セッション開始トークン (ADR-0017) の発行・検証 (registry-only)・`computeAnchoredChainRoot`。署名鍵は checkpoint と同一系統を流用。未登録 keyId でも `keyId` と `unknownKey: true` を返す (#329) |
| `checkpointKeys/registry.ts` | append-only 公開鍵レジストリ (本番鍵) |
| `checkpointKeys/keyValidity.ts` | 鍵の有効期間 / 失効判定の**単一実装** (#233)。checkpoint 鍵と出題者鍵の両方を構造型で受ける |
| `checkpointKeys/localKeys.ts` | ローカル開発鍵置き場 (gitignore 済み。無ければ `npm install` の postinstall / e2e の setup / doctor が `localKeys.ts.example` から作る。#338) |
| `fingerprint.ts` | ブラウザフィンガープリント |
| `verification.ts` | チェーン外検証ユーティリティ (content replay 等)。`verifyPoSW` の反復は**同期 SHA-256** (`hashUtils.ts` の `iterateSha256HexSync`、`@noble/hashes`) で計算する (#267) |
| `utils/hashUtils.ts` | `deterministicStringify` / `computeHash` (WebCrypto, async) / `iterateSha256HexSync` (PoSW 反復の同期版。`computeHash` を n 回 await した結果とビット単位で一致することを `__tests__/poswSync.test.ts` が固定ベクタで縛る) |
| `poswWorker.ts` | PoSW Web Worker 本体 |
| `attestation.ts` | 人間認証クライアント |
| `fileProcessing/` | ZIP / JSON 解析。`zipBudget.ts` が ZIP 展開の上限 (エントリ数・実バイト予算) と予算付きリーダーを持つ。`parser.ts` の `extractAllProofsFromZip` は `{ proofs, failures }` を返し、proof の命名 (`isProofExportFilename`) に当たるのに読めないファイルを黙って捨てず `failures` に集める (#292。verify Web の ZIP 読込も同じ判定を共有する)。`proofLanguage.ts` は proof 由来の自己申告 `language` を allowlist (`languageDetection.ts` の `KNOWN_LANGUAGES`) に落とす (#248)。`submissionSources.ts` の `matchSubmissionSources` は提出物 (ZIP の同梱ソースと `proof.content`) の対応規則と照合の**単一実装**で、verify-cli と verify Web が同じ結論を出す (#293。規則と重さは system-spec §5.2.1)。期待ソース名は `exportNaming.ts` が editor の export と同じ手順で作る (言語 → 拡張子の表 `LANGUAGE_FILE_EXTENSIONS` もここ 1 箇所。editor はこの表と `createExportNamer` から ZIP 内のファイル名を作るので、名前の付け方を editor 側で変えると検証が「ソース欠落」を出す)。`createExportNamer` は授業・課題の問題文の名前 `<base>_problem(_N).md` も proof と同じ番号で返し (#778)、`isSubmissionSourceEntry` はその形をソースの候補から外す (証明の対象外の平文。外さないと孤立ソースの警告になる) |
| `types.ts` (実体は `types/`) | 全公開型 |
| `assurance.ts` | 三層保証語彙 (ADR-0020)。`deriveAssurance` が実証拠のみから整合性/時刻アンカー/著述性(advisory) を導出。verify(web)/verify-cli が同一実装を使う (表示の食い違い防止)。**自己申告 `proof.mode` を入力に使わない・provenance を判定に昇格させない**。temporal の `anchored` は最後の署名 cp が最終イベントを指し (`coverage.terminalAnchored` → `signedCheckpoints.terminal`)、token と cp の sessionId が一致する (`sessionTokenMismatch`) ときだけ (#295)。どちらも `poswSkipped` と同じく必須入力 (optional にすると渡し忘れが overclaim に倒れる) |
| `analysis/` | 分析層フレームワーク (ADR-0009)。`runAnalysis` + 差し替え可能な `Analyzer` 群。`runAnalysis` は分析器ごとに期限 (`ANALYZER_TIMEOUT_MS` = 10 秒、`{ timeoutMs }` で上書き) を付けて走らせ、結果を `AnalysisReport.analyzerStatus` (`ok` / `failed` / `timeout` / `invalid-output`) に残す (#301。不変条件 14) (automation / transcription-topology / focus-burst の第一次ヒューリスティック + pureTyping)。検証と**直交**する advisory のみ・判定しない。`automationAnalyzer` は webdriver/headless GPU に加え **合成打鍵 (`KeystrokeDynamicsData.isTrusted===false`, ADR-0018)** も数える。`templateInjectionAnalyzer` (#416) は `templateInjection` の `data.content.length` の合計 (テンプレートで入った文字数。自己申告の `contentLength` は使わない) と `contentChange` の `insertedCharCount` の合計を並べる **severity `info` 固定**の signal で、`isPureTyping` の定義も `reviewPriority` も変えない (starter を持つ正規の proof で全員 notice にならないため。閾値で振り分けない = ADR-0023)。`typingPatternAnalyzer` は旧 `TypingPatternAnalyzer` (打鍵動態) を `keystroke-content-consistency` 次元の advisory signal に折り込む (旧 verify TypingPatternCard を廃止・判定ゲージは持ち込まない・critical でも notice 止まり・dwell<30 で黙る ★6b)。`analysis/eval.ts` は **実証評価** (W5): ラベル付きコーパス → `evaluateAnalysis` が混同行列/閾値スイープ/genuineSignalRate を純粋関数で算出。**ゲート: 実測まで heuristic を `review` に昇格しない** (収集手順は docs/analysis-eval-protocol.md、ランナーは `__tests__/analysisEvalCorpus.test.ts`)。`analysis/bundle.ts` は **Tier A バンドル** (ADR-0024): `buildAnalysisBundle` が content-free な `{processSummary, analysis, assurance}` を束ねる (events/source/fingerprint なし。ただし参照をそのまま束ねるので自由記述と余分なフィールドは素通しする)。`analysis/aggregateBundle.ts` は **Tier S バンドル** (ADR-0024 Amendment, #304): `toAggregateBundle` が Tier A から数値とカテゴリだけを **allowlist で 1 項目ずつ**書き出す (自由記述・`analyzerId`・event index なし、未知の列挙値は `other`、非有限数は `null`)。**spread・`Object.assign` で作らない** (型の narrow では実行時の余分なフィールドが残る。`aggregateBundle.test.ts` が `SECRET-*` で固定)。両バンドルに固定文言 `DERIVED_VIEW_NOTICE` を載せる。`analysis/cohort.ts` は **コホート基準** (ADR-0025): `computeCohortBaseline`/`positionInCohort` が数値とカテゴリだけの `CohortBundleInput[]` (Tier A / Tier S のどちらも渡る) から頑健分布 (中央値/IQR・個票非保持) と提出物の位置 (percentile/IQR距離) を算出。**advisory・外れ値≠違反・小N ガード** |
| `exam/` | 試験モードの暗号コア (ADR-0006)。封印 `.tcexam` の build/verify(署名)/decrypt(Argon2id+AES-256-GCM)、`computeExamChainRoot`、`parseExamPackageManifest`、grader 用 `verifyExamBinding`。`examStarter.ts` は封印 starter と `templateInjection` の `data.content` の照合 (#718。v2 だけ、v1 は `not-evaluated`。自己申告の `contentHash` などは使わない。規則は system-spec §6.4 手順 5b)。`examLanguage.ts` は許可言語の判定の**単一実装** (#727。`allowed.languages` ∪ v2 の該当問題の starter の言語、完全一致、空 = 制限なし)。grader の `proof.language` 照合 (手順 5c) と editor の言語の選択・変更・実行・HTML プレビュー開始の境界が同じ関数を呼ぶので、別に書き起こさない。root 式は `proof.exam` 有無で分岐。N問バンドル codec は `examBundle.ts` (`tcexam-exam/1`)。**授業モードの平文配布 `classPackage.ts` (ADR-0014, `tcclass/1`) も同居** — 暗号を持たず `parseExamBundle` を平文で再利用する `parseClassPackage`/`encodeClassPackage` |
| `specs/` | 仕様別の検証 (#809 / ADR-0053。不変条件 4・15)。`identify.ts` (registry と識別・legacy 1.2.0 の構造の検査)、`legacyTypingProof.ts` (legacy 1.2.0 の結果を共通の結果へ写す)、`verifyProofBySpec.ts` (入口・trust snapshot の digest)、`types.ts` (結果の型。名前は内部用で、公開する名前は #811 で確定)。対応表と結果の各軸は system-spec §6.5 |
| `examAuthorityKeys/` | 出題者 (問題署名) 公開鍵レジストリ (ADR-0006)。`checkpointKeys/` と**別系統・同型** (append-only、`registry.ts` 本番 + gitignore 済みの `localKeys.ts`) |
