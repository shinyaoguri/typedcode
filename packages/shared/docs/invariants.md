# packages/shared — 不変条件の全文

[AGENTS.md](../AGENTS.md)「重要な不変条件 (壊さないこと)」の全文 (理由・例外・回帰テスト)。番号と並びは AGENTS.md と同じで、変えない (コード・テスト・他の文書が番号で参照する)。不変条件を足す・変えるときは、ここに全文を書き、AGENTS.md には見出しを 1 行だけ置く。

1. **ハッシュチェーン**: `h_i = SHA-256(h_{i-1} || JSON(event_i) || PoSW_i)`。JSON シリアライズはキー順序を決定的にする (`hashUtils.ts:deterministicStringify`)。**順序が崩れると既存の証明がすべて検証不能になる**
2. **PoSW 反復数**: `POSW_ITERATIONS` ([`src/version.ts`](../src/version.ts)) 固定。検証側もこの値を期待する。**変更は破壊的**で、proof format version bump が必要。反復数は [ADR-0045](../../../docs/adr/0045-lower-posw-iterations-for-recording-throughput.md) で 10,000 → 1,000 に下げると決め、proof・署名 cp・token の 3 系統の分岐とあわせて #810 の新仕様で実装する (#611 を #810 に畳んだ。proof の版 1.3.0 は作らない。[ADR-0053](../../../docs/adr/0053-versioned-verification-contracts.md) §5)
3. **InputType の許可/禁止リスト**: `InputTypeValidator.ts` の `ALLOWED_INPUT_TYPES` / `PROHIBITED_INPUT_TYPES` がピュアタイピング判定の唯一の真実。新しい入力タイプを追加する際は判断を ADR に残す ([docs/adr/0005-input-type-policy.md](../../../docs/adr/0005-input-type-policy.md))
4. **`PROOF_FORMAT_VERSION`**: 既存 proof との互換性ある変更なら据え置き。互換性破壊なら bump 必須。現在 **1.2.0** (1.1.0=exam root 束縛 ADR-0006、1.2.0=session anchor ADR-0017。どちらも加算的で `MIN_SUPPORTED_VERSION` は 1.0.0 据え置き)。**検証器は `verifyProofFile` の入口で `proof.version` を `classifyProofVersion` (厳密 parse) で分類する (#223)**: 下限未満・不正形式は reject、既知 major を超えるものは reject せず `versionStatus: 'newer'` の warning。ゆるい `parseVersion` / `compareVersions` はゲートに使わない (`'abc'` が NaN で通る)。exam も同様に `parseExamPackageManifest` が `formatVersion` を `EXAM_PACKAGE_FORMAT_VERSION` と、`verifyExamBinding` が `examProofVersion` を `EXAM_PROOF_VERSION` と照合する (`examProofVersion` 欠落は 1)。**proof の version を bump するときは、旧検証器が `newer` warning を出す前提で意味の変わる変更かどうかを判断し、`MIN_SUPPORTED_VERSION` / `EXAM_*_VERSION` の扱いを同じ PR で決める**。**仕様別の入口 `verifyProofBySpec` (`specs/`。#809 / [ADR-0053](../../../docs/adr/0053-versioned-verification-contracts.md)) は別の規則で識別する**: `version` を静的な registry への完全一致で引き、いまは `1.2.0` だけを legacy の検証器 (`verifyProofFile`) で読む。他の正しい形の版 (1.0.0・1.1.0 も) は `unsupported`、識別子・構造の不正は `malformed` で、どちらも検証器を呼ばない。registry に版を足すときは、その版の凍結 fixture と検証器を同じ PR で足し、大小比較や「同じ major だから」で対応済みにしない。公式 Web / CLI はまだ `verifyProofFile` を直接使うので、上のゲート (1.0.0 以上を受理) が現役 (切り替えと古いゲートの撤去は #811)
7. **anchored root 式の二重定義を一致させる** (ADR-0017): casual/class の anchored root は `computeAnchoredChainRoot` (verifier) と `HashChainManager.generateAnchoredInitialHash` (editor) の **2 箇所**に `SHA256(fp ‖ localNonce ‖ serverNonce)` を持つ。exam の `computeExamChainRoot`/`generateExamInitialHash` と同じ轍。式を変えるなら両方＋テストを同時に直す
5. **`CheckpointManager`** はステートフル。`shouldCreateCheckpoint` の判定は最終 cp の eventIndex / 時刻に依存する。`setCheckpoints` で復元する際は内部状態も再構築すること (実装済み)
6. **検証は cp の間隔を仮定しない**: `verify` 側は cp の存在を補助メタデータとしてのみ扱い、未署名 cp の sampling は信頼しない ([docs/adr/0004-verifier-checkpoint-stance.md](../../../docs/adr/0004-verifier-checkpoint-stance.md))
8. **`isPureTyping` の判定点は 1 つ** (#235): `structuralEdit.ts` の `evaluatePureTyping` だけが決める。export 時の自己申告 (`TypingProof`) と採点側の再計算 (`verifyProofMetadata`) が同じ関数を呼ぶので、proof に焼かれる値と検証器の結論が食い違わない。**別の場所に式を書き足さないこと**。なお `metadata.bulkInsertEvents` は `isSuspiciousBulkInsert` の素のカウントのままで、こちらは申告値との完全一致を要求するので定義を変えると既存 proof が invalid になる
9. **ZIP エントリの展開は予算経由** (#234): `fileProcessing/zipBudget.ts` の `ZipExtractionBudget` + `readZipEntryBytes` / `readZipEntryText` だけが JSZip からバイトを取り出す。ヘッダの申告 `uncompressedSize` は攻撃者が書ける値なので `assertZipWithinBudget` は**早期 reject 専用** (それだけでは 300 MiB を 1 バイトと名乗る ZIP を素通しする)。上限は展開中の**実バイト**で見る。`entry.async(...)` の直接呼び出しは `__tests__/zipReadPolicy.test.ts` が禁止する。申告値が読めないエントリは fail-closed で拒否するが、JSZip が 0 バイトのエントリに作る形 (`_data` が申告値を持たない thenable + `STORE`) だけは 0 として数える (#447。空のタブを含む export を通すため。形の判定を緩めると `zipBudget.test.ts` の部分一致テストが止める)
10. **registry の日時判定は 1 箇所** (#233): `checkpointKeys/keyValidity.ts` の `checkRegistryKeyValidityAt` だけが `validFrom` / `validUntil` / `revokedAt` を解釈する。署名 cp (anchor=`serverTimestamp`) / sessionStartToken (`issuedAt`) / 出題者鍵 (`releaseTime`) の 3 消費者はここを呼び、**文言づけだけ**を各自で持つ。日時は system-spec §9.4 の手書き運用なので **parse 不能なら entry 単位で信頼しない** (fail-closed) — かつては 3 箇所とも `Number.isFinite` ガードで検査ごと素通りし、失効済み鍵が警告すら出さずに通っていた。出荷 registry の形式は `__tests__/registryFormat.test.ts` が縛る (`Date.parse` は `2026-02-30` をロールオーバーして受け入れるので、厳密 ISO 正規表現 + 往復比較の両方が要る)
11. **proof 由来の自己申告文字列は表示前に allowlist へ落とす** (#210 / #248): `proof.json` は攻撃者が組み立てられる入力で、型注釈は `JSON.parse` の結果を cast しただけ。表示層は値を補間する (verify は `className`、verify-cli は stdout) ので、`language` は `fileProcessing/proofLanguage.ts` の `normalizeProofLanguage` を通す (集合外は `'unknown'`)。allowlist の元は `languageDetection.ts` の `KNOWN_LANGUAGES` **1 箇所**で、別に書き起こすとドリフトする。`mode` は verify 側の `normalizeProofMode` が同じ契約を持つ。**表示に使う自己申告フィールドを増やすときは、まず正規化の置き場を決めること**
12. **分析器はハッシュ対象のフィールドしか見ない** (#328): `description` / `insertLength` / `selectedText` などはハッシュに入らず、proof.json を書き換えても検証が通る。`runAnalysis` は入口でイベントを `verification.ts` の `pickHashedEventFields` (ハッシュ対象フィールドの**単一定義**。`verifyChain` も同じ関数を使う) に射影してから分析器へ渡す。挿入文字数は `structuralEdit.ts` の `insertedCharCount` (`data` の長さ) で数え、`processSummary` と分析器で定義を分けない。射影を外す・ハッシュ対象外のフィールドを分析に使う変更は、`analysisOrchestrator.test.ts` の「対象外フィールドを書き換えても出力が変わらない」テストが止める
13. **token の検証失敗は改ざんではなく時刻アンカーの失敗** (#329): `verifyInitialHashRoot` は token の未登録 keyId・署名不正・`fingerprintHash` の不一致で `valid:false` を返さない。serverNonce 込みの式で root を照合し、合えば `valid:true` / `rootAnchored:false` / `anchorFailure` (`token-unknown-key` / `token-invalid` / `token-fingerprint-mismatch`) を返す。`verifyProofFile` はそれを `rootAnchorFailure` に写し、総合の `valid` と `errorMessage` の連鎖に入れる (`metadataValid` は落とさない)。**`rootAnchored` の意味 (検証済みの token で root が成立した) は変えない**。連鎖に入れ忘れると、CLI の Error 行に成功の文言 (`All hashes verified successfully`) が出る。root が合わない (serverNonce の書き換え) のは従来どおり改ざん。`verification.untrustedSessionToken.test.ts` が full モードで固定する
14. **分析器の失敗は signal にせず `analyzerStatus` に出す** (#301): `runAnalysis` は throw (同期・非同期)・期限切れ・契約に合わない出力を、その分析器の `analyzerStatus` に `failed` / `timeout` / `invalid-output` として残し、他の分析器を止めない。失敗を signal にすると、signal 0 件の「手掛かりなし」と区別できなくなり、`reviewPriority` の集約にも混ざる。期限切れの後に解決した結果は捨て、決着したら期限のタイマーを必ず `clearTimeout` する (残すと verify-cli の自然終了が最大 10 秒遅れる)。契約に合わない signal (severity が 3 値の外・score / confidence が finite でない・evidence が配列でない・summary が string でない・オブジェクトでない) は捨てて `reviewPriority` に寄与させない (かつては未知の severity で `reviewPriority` が NaN、`score: Infinity` で 1 になった)。`summarizeAnalysisForAssurance` は ok の分析器が 0 なら undefined を返し、著述性を「分析未実行」(null) に倒す。`durationMs` のような実行ごとに変わる値は status に入れない (同じ入力 → 同じ出力のテストと `--analysis-json` の差分安定のため)。`analysisOrchestrator.test.ts` の `runAnalysis analyzer status (#301)` が固定する
15. **仕様別の結果は自由文を読まず、legacy より甘くしない** (#809): `specs/legacyTypingProof.ts` は `FullVerificationResult` の構造化フィールド (`chainFailure`・`typingProofHashValid`・`eventMetadataValid`・`rootAnchorFailure.code`) と各検証の `keyStatus` だけから検査と鍵の信頼を写す。`reason` / `errorMessage` を parse しない (要る情報が自由文にしか無ければ、下位の結果に code を**足す**。既存フィールドの値と判定は変えない)。走っていない検査は `not-checked` にし、`pass` にしない。整合性 (`integrity`) は `checks` だけから導く (`fail` があれば `failed`、`fail` が無く `not-checked` があれば `partial`)。**legacy の `verifyProofFile` が `integrityValid: false` にする proof に `proven` / `partial` を返さない** (`specIntegrity.test.ts` の突き合わせが固定する)。この `integrity` は `assurance.integrity` (ADR-0020。署名 cp・token の失敗を時刻アンカー層に数える) とも `integrityValid` (問題束縛を含まない) とも別の値。鍵の判定 (`checkRegistryKeyValidityAt`) を状態へ写すのは `registryKeyTrustStatus` 1 箇所。問題束縛は入口が自分で `verifyExamBinding` を呼んで確かめ、呼び出し側の「検証済み」の申告を受けない。入口は時計とネットワークを使わず、`trust` と `evaluationTime` を必須で受ける (既定の registry に落とさない)。入力は `unknown` で受けるので、構造の検査を通った入力で検証器が例外を投げる経路を作らない (`specStructureFuzz.test.ts`)
16. **鍵の環境は署名の検証の後で判定する** (#321 / ADR-0002): `registry.ts` のエントリは `environment` (`production` / `staging`) が必須 (型と `registryFormat.test.ts`)。`localKeys.ts` の鍵は `checkpointKeys/index.ts` の `asDevelopmentKeys` が常に `development` にする。信頼する範囲は `checkpointKeys/keyEnvironment.ts` の `trustedCheckpointKeyEnvironments` 1 か所で決め (既定は production + development。verify-cli と verify が同じ関数を呼ぶ)、`verifyInitialHashRoot` と `verifySignedCheckpoints` は全鍵で検証した後に判定する。範囲の外の鍵の証拠は「無い」扱いにして `rootAnchorUntrustedKey` / `untrustedKeys` を返し、`valid` / `integrityValid` / `metadataValid` は落とさない (`rootAnchorFailure` にしない。署名が壊れていれば従来どおり失敗)。環境の無いエントリは信頼しない (fail-closed)。**`verifyProofBySpec` は渡された鍵の一覧そのものを信頼する** (`ALL_CHECKPOINT_KEY_ENVIRONMENTS`) ので、アプリから呼ぶ側 (#811) は registry 全体を渡さず、信頼する環境の鍵だけを渡す。固定は `verification.keyEnvironment.test.ts`
