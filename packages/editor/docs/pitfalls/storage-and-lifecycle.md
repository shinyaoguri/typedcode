# packages/editor — 罠: 保存・タブ・インスタンスのライフサイクル

タブを閉じる・消す経路、IndexedDB のスキーマと接続、二重起動の検出、ページの離脱、スクリーンショットの保存を触るときに読む。[AGENTS.md](../../AGENTS.md)「よくある罠」に見出しがあり、ここが本文 (理由・経緯・回帰テスト)。罠を足すときは、ここに本文を書き、AGENTS.md には見出しを 1 行足す。

`core/`・`services/`・`ui/` などで始まるコードのパスは `packages/editor/src/` から見たもの。

- **beforeunload は「確認」と「状態保存」を別のフラグで分ける (#445)**: ハンドラは `app/beforeUnloadGuard.ts` の `handleBeforeUnload`。`ctx.skipBeforeUnload` (リセット確定) は**保存 (`saveToStorageSync`・`sessionActiveKey`) も確認も飛ばす**ので、リロード復元が要る遷移では使えない。表示言語の切替は `ctx.skipUnloadConfirm` を立てる (**確認 `preventDefault` だけ抑止し、保存は通常どおり**)。新しく「作業が続く遷移」を足すときは後者を使う。ui コンポーネントは `AppContext` を持たないので、コールバックで受ける
- **`SingleInstanceGuard` の判定は Web Locks で、時間に依存させない (#494)**: 二重起動は `navigator.locks.request('typedcode-instance-guard:<名前>', { ifAvailable: true })` で検出する (名前は保存領域ごと = `storageKeys.instanceGuardNamespace()`。旧来の入口はモード名、作業スペースは `w:<作業スペースの名前>` = #646。別モード・別の作業スペースは共存)。取れたら `dispose()` まで持ち続け、取れなければ既存ありで `duplicate-instance` を出す。BroadcastChannel (同じ名前) は heartbeat (`instance-active`) と、`navigator.locks` が無い環境 (と request が失敗したとき) の ping → pong (500ms 待つ) に残している。ping → pong を判定の主に戻さない: `window.open` で開いた同じオリジンの popup は開いた側と同じ main thread で動くので、popup の初期化の長いタスクの間は開いた側が ping に答えられず、500ms が先に切れてすり抜ける (#494 で実測)。lock を持つ側は lock が無い環境のインスタンスのために pong を返し続ける。bfcache 中のページは lock を持ったままで、別のページが同じ lock を求めると Chromium がそのページを bfcache から追い出す (`WebLocksContention`。戻ると読み直しでガードが判定し直す)。凍結中 (bfcache 以外) のページも lock を持ち続けるので、後から開いた側が止まる (#237)。E2E は `packages/e2e/tests/multi-instance.spec.ts` (`window.open` で開いた popup)
- **`SingleInstanceGuard` はページを離れるとき (`pagehide`) にだけ破棄する (#483)**: 破棄 (lock の解放と BroadcastChannel を閉じる) を `beforeunload` に置くと、離脱確認で「このページに留まる」を選んだときにアンロードされないのにガードだけ外れ、2 つ目のタブが正規インスタンスとして起動する。`pagehide` は `persisted === false` (実際に離れる) のときだけ `dispose()` し、bfcache に入る (`persisted === true`) ときは破棄しない (復元されたページのガードが生きたままになる。凍結中に開かれた別タブとの競合は、`navigator.locks` が使えず ping → pong に戻った経路でだけ成立し、`services/InstanceConflictMonitor.ts` が `instance-active` の受信・`resume`・`visibilitychange`・`pageshow` を契機に所有者を確かめて、譲る側を read-only にする = #237 PR-3)。ガードの破棄を `beforeunload` に戻さない。E2E は `packages/e2e/tests/multi-instance.spec.ts` (離脱確認を dismiss してから 2 つ目のタブを開く)
- **スクリーンショットは「チェーンに記録できるときだけ」保存する (#503)**: export ZIP の manifest に入る画像は、必ずハッシュチェーン上の `screenshotCapture` に裏付けられていなければならない (shared の `isChainBackedImageHash` が見張り、裏付けの無い画像は tampered になる)。`ScreenshotTracker.handleCapture` は `callback` (チェーンへの記録先) が無いとき**保存しない** (保存を先にして event だけ省くと画像だけが残る)。試験ゲート中などタブが無い間は `captureEnabled` が true のまま callback が null で撮影が走るので、`captureEnabled` だけに頼らない。撮影経路を足すときも「保存と event 記録を対にする」。回帰は `tracking/__tests__/ScreenshotTracker.test.ts`、経路全体は `packages/e2e` の exam round-trip
- **タブを閉じる後始末は順序が要る (#342)**: `TabManager.closeTab` / `closeAllTabs` は閉じたタブを `retireTab` に渡し、**PoSW の確定 (`waitForQueueDrain`) → IndexedDB への append 完了 (`EventRecorder.whenTabSettled`。`main.ts` が `setTabSettleBarrier` で注入) → 閉じたタブとしての書き込み (`archiveTab`。exam だけは tabs 行と events 行の削除) → `TypingProof.dispose()` (Worker 終了)** の順に進める。`waitForQueueDrain` だけでは足りない: events 行の append は確定後の `.then` (`EventRecorder.record`) で走るので、先に行を消すと tabs 行の無い events 行 (孤児) が残る。計算中のイベントは捨てない。**`recordToAllTabs` / `recordSessionSnapshotTo` が使う `recordToTab` も `record()` と同じく確定ごとに 1 件ずつ `saveEventToIndexedDB` で append し、`inFlightByTab` に載せる** (#471。デバウンス保存だけに任せると、直後の `record()` の seq だけが先に入って events に欠番ができ、閉じたタブの events 行が削除の後に孤児で残りうる)。append は確定の通知順に始めるため、`await` より前の同期区間で呼ぶ。`closeTab` は同期で boolean を返し、後段は非同期 (待つなら `whenTabsRetired()`)。`TypingProof` を捨てる経路を足すときは `dispose()` を呼ぶ。**閉じた後に届いた記録の要求が閉じたタブに載らないのは、`closeTab` が `retireTab` より前に同期で `this.tabs` から外すから** (#788。`EventRecorder` の記録の入口はどれも呼ばれた時点で TabManager からタブを引く。保存層の `appendEvent` は tabs 行の無いタブにも書くので、防いでいるのはこの 1 行だけ)。**行の削除は、走っている保存をすべて待ってから行う** (#145 / #833): デバウンスの保存 (`currentSavePromise`) に加えて、`flushToIndexedDB` が直接走らせる保存 (`flushPersists`) も待つ。flush の保存を `currentSavePromise` に載せないのは、デバウンスと再試行 (#543) がそれを見て何もせずに戻り、flush 末尾の同期状態の確定 (#456) の条件も変わるため。`persistAll()` を直接呼ぶ経路を足すときは、削除が待てるように同じ集合に登録する。回帰は `ui/tabs/__tests__/TabManager.closeTab.test.ts`
- **exam を除き、利用者の明示の操作なしに、コードとイベントを IndexedDB から削除しない (#317 / ADR-0057)**: 明示の操作は、復旧ダイアログの「完全に削除する」と設定メニューのリセットだけ。タブを閉じる・テンプレートを取り込むと、`TabManager.retireTab` は (#342 の順序のまま) `SessionStorageService.archiveTab` で、未保存のイベントの add・tabs 行の `archived: true` + `archivedAt` の put・書き込み位置の put を **1 つの transaction** で書く。失敗・中断・所有権の喪失・hash の食い違いでは何も書かず、閉じる前の行が残る (**削除へ倒さない**)。`deleteTab` を使うのは exam (`closedTabPolicy: 'delete'`) だけ。`archived` は tabs 行に置き、`tabProgress` には入れない。**この変更のために `DB_VERSION` を上げない** (index を作らず、一覧は tabs を読んで絞る)。閉じたタブは `loadTabs` と `hasExistingSession` から外す (#145)。復旧ダイアログの「新規」の既定は `archiveSessionTabs` (残す)。最後のタブを閉じてもスクリーンショットを消さない (exam を除く)。開き直し (`reopenArchivedTab`) は、行の `archived` を外して `sessionId` を今のセッションへ書き直す。**署名は、その proof が結びついたセッション (署名済み cp の sessionId → root の token の sessionId) で続ける** (`attachSignedCheckpointService`。1 つの proof に sessionId を混ぜると検証器が拒否する)
- **IndexedDB のバージョンマイグレーション**: session DB のスキーマは `SessionStorageService` の `DB_VERSION` で上げ、`onupgradeneeded` に `oldVersion` で分けた移行を足す (2 = screenshots、3 = unprovenContents #413、4 = tabProgress #627。4 は既存の行を書き換えず、旧版の位置は tabs 行から読む)。既存の行の形を変える移行は shared に移行関数を置く。shared の `STORAGE_FORMAT_VERSION` は localStorage 用の整数で、`DB_VERSION` とは別に管理している (ストアを足すだけの 1 → 2 / 2 → 3 / 3 → 4 では据え置いた)。**版を上げた DB は、前の版のエディタでは開けない** (`open` が VersionError になり起動に失敗する)。版を上げる変更が production に出た後は、その前の版へ配信を巻き戻すと、新しい版で一度開いた利用者が起動できなくなる。移行のテストは `services/__tests__/SessionStorageService.test.ts` の「version 2 の DB を開き直す」形で書く
- **IndexedDB の接続のライフサイクル (#325)**: `SessionStorageService` は open の `blocked` で待ち続けずに `SessionStorageBlockedError` で reject する (起動失敗の画面で他のタブを閉じるよう案内する。遅れて success した接続は握らずに閉じる)。開いた接続が `versionchange` を受けたら閉じて (新しい版の open を塞がない) 以後の操作を `SessionStorageUnavailableError('versionchange')` にし、強制的な `close` (サイトデータの削除など。自分の `close()` では発火しない) では 1 回だけ開き直して、失敗したら `SessionStorageUnavailableError('closed')` にする。どちらもリスナー (`setOnConnectionLost`) で main が通知を出す。**接続を失っても `initialized` と `sessionId` を落とさない**: `TabManager.saveToIndexedDB` は未初期化なら書かずに成功扱いにするので、落とすと保存の失敗が `synced` に見える (失敗は `degraded` / `failed` で出す)。各メソッドは `this.db` を直に触らず `getDb()` を経る。`getDb()` は 1 本の `connectionReady` (普段は解決済み、強制 close の後は開き直しの試み) に `.then` を連ねるので、開き直しの間に呼ばれたものも含めて呼び出し順に transaction を作る (書き込みの逐次性 = 不変条件 5)。起動処理 (`initializeApp`) の reject は `boot()` が拾って `boot-failure` を出すので、起動中の例外を握りつぶして続行しない。回帰は `services/__tests__/SessionStorageService.connection.test.ts` と e2e の `fault-storage.spec.ts`
