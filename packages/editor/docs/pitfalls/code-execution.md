# packages/editor — 罠: コード実行 (C / C++・JS / TS・Python・ターミナル・HTML プレビュー)

`executors/`・`execution/`・`terminal/`・`ui/` のプレビューと、`@wasmer/sdk`・Pyodide の更新を触るときに読む。[AGENTS.md](../../AGENTS.md)「よくある罠」に見出しがあり、ここが本文 (理由・経緯・回帰テスト)。罠を足すときは、ここに本文を書き、AGENTS.md には見出しを 1 行足す。

`core/`・`services/`・`ui/` などで始まるコードのパスは `packages/editor/src/` から見たもの。

- **`@wasmer/sdk` を上げたら本番ビルドで C を動かす (#364)**: 0.19 以降の SDK は worker と wasm-bindgen の glue を `new URL(..., import.meta.url)` で自分で解決し、本番ビルドの Vite はそれを依存の欠けた静的アセットとして出す。`vite.config.ts` の `wasmerSdkBundledWorkers` がビルド時だけバンドル済みチャンクに差し替えている (書き換え対象の式が見つからなければビルドを止める)。**glue は `build.rollupOptions.output.codeSplitting.groups` の `wasmer_sdk_js` で専用のチャンクに固定している** (#727): 自動の分割に任せると、依存グラフ次第で rolldown のランタイムヘルパ (`\0rolldown/runtime.js`。groups の `test` には渡ってこないので直接は固定できない) が glue のチャンクに同居し、ヘルパを import するエントリから glue が static に届いて、not-found を含む全ページが約 190KB の glue を modulepreload で読む。グループを外さない (`production-build.spec.ts` の not-found が見張る)。dev サーバでは壊れ方が出ないので、本番ビルドで C の hello を実行する nightly の検査 (`packages/e2e/tests/production-build.spec.ts` の `@nightly`。毎晩 `e2e-nightly.yml` が回す) を、SDK を上げる PR で手元でも回す: `NIGHTLY=1 npm run test:build -w @typedcode/e2e -- --grep @nightly` (dev サーバの C / Python の実行と #489 の行番号は `NIGHTLY=1 npm run test -w @typedcode/e2e -- --grep @nightly code-execution-c-python`。clang の webc・Pyodide を外部から取るので PR ゲートには載せていない。#589)。同じ設定の alias で、WISP ネットワーク専用の `@mercuryworkshop/wisp-js` (AGPL-3.0) を `executors/c/wispClientStub.ts` に差し替えて配信物に入れていない。sandbox の `network` を有効にしない
- **C / C++ の利用者のソースには何も前置しない (#709)**: stdout の非バッファ化 (constructor の `setvbuf(stdout, NULL, _IONBF, 0)`) は、`CExecutor.ts` の `STDOUT_SUPPORT_SOURCE` を `__typedcode_stdout.c` / `.cpp` (利用者のソースと同じ拡張子) として、clang の 2 つ目の入力でコンパイル・リンクする。利用者のソースに `#include` や `#line` を足さない (足すと、`stdio.h` の書き忘れが通り、利用者の翻訳単位に `FILE` / `EOF` が入り、行番号がずれる = #489)。支援コードの診断は `parseErrors` がマーカーにしない。C++ では支援コードも `.cpp` にする (`-std=c++17` は C の入力に付けられない)。stdin が pipe (#707) で、プログラムから見て端末ではないので、**非バッファ化は外さない** (外すと、改行の無いプロンプトが入力の前に出なくなる)。wasi-libc (musl) の `setvbuf` はバッファを渡されたときだけ効くので、利用者の `setvbuf(stdout, NULL, _IOFBF, n)` は非バッファのまま (ネイティブとは違う)。回帰は `@nightly` の `packages/e2e/tests/code-execution-c-stdout.spec.ts`
- **C++ のコンパイルは `-xc++` を渡さず、libc++ の版の `#warning` を `-include` の guard で黙らせる (#871)**: C++ として扱わせるのは拡張子 `.cpp` (ドライバが cc1 に `-x c++` を渡す)。入力ファイルの後ろの `-xc++` は効かずに `-Wunused-command-line-argument` を出すだけなので、戻さない。clang 16 と libc++ 19 の食い違い (#573) で、利用者の `<cstdio>` などから `<__config>` 経由で出る `#warning "Libc++ only supports Clang 17 and later"` は、system header の中でも出る診断で、止めるマクロも無い。そこで `CppExecutor` が `/workspace/typedcode-libcxx-guard.h` を sandbox に置いて `-include` させ、`-W#warnings` を無視させた範囲で `<__config>` を 1 回だけ取り込む (push / pop)。`-include` は利用者のソースと stdout の支援コード (#709) の両方の翻訳単位に掛かるので、支援コードの側では黙らせない (手当てを 1 か所にまとめ、版の揃った webc に替えたら guard ごと外す)。**`-Wno-#warnings` に替えない** (利用者の `#warning` も消える)。利用者が libc++ のヘッダより前に `_LIBCPP_*` を `#define` しても、`<__config>` が先に読まれるので効かない。回帰は `@nightly` の `packages/e2e/tests/code-execution-cpp-warnings.spec.ts`
- **C / C++ のリンクには `-lwasi-emulated-process-clocks` を渡す (#714)**: clang の webc のドライバは `-D_WASI_EMULATED_PROCESS_CLOCKS` で `<time.h>` に `clock()` を宣言させるのに、リンクには `-lc` しか渡さない。`CExecutor.ts` の `LINK_ARGS` を外すと `clock()` が `undefined symbol: clock` で落ちる (ライブラリは webc の sysroot にある)。この `clock()` は CLOCK_MONOTONIC の経過 (実時間) で、CPU 時間ではない。`CLOCK_PROCESS_CPUTIME_ID` も実時間を返すので、CPU 時間は測れない。回帰は `@nightly` の `packages/e2e/tests/code-execution-c-clock.spec.ts` (眠っている間も進むことを固定してあり、CPU 時間を返すランタイムに変わると赤くなる)
- **HTML プレビュー iframe は opaque origin (#291/#299)**: `#preview-iframe` は `sandbox="allow-scripts allow-modals allow-forms"` の 3 トークンだけを持つ。**`allow-same-origin` を足さない** (`allow-scripts` と併用すると同一 origin の学習者 HTML が親 DOM・localStorage・proof の IndexedDB に届き、sandbox 自体も外せる)。`allow-top-navigation*` / `allow-popups` / `allow-downloads` も付けない = トップレベル遷移・ポップアップ・ダウンロードは不可。親の `crossOriginIsolated` (COOP/COEP `credentialless`) はこのままで維持される。内容の投入は **`srcdoc` に一本化** (Blob URL / `src` と混在させると残った srcdoc が優先され再表示が空になる = #299。placeholder は `removeAttribute('srcdoc')` + `about:blank`)。親から `contentWindow` の中身 (scrollX 等) には触れないので、親子通信は **postMessage + 受信側で `e.source` を検査** (opaque origin なので `e.origin` は `'null'`)。スクロール保存/復帰は `BrowserPreviewPanel` が末尾に注入するブリッジ script 経由。srcdoc は親の CSP (#411) を継承するので、学習者の inline の script とイベントハンドラのために親の `script-src` に `'unsafe-inline'` が要る (外すのはプレビューを専用ページにする #897)。外部のサイトの画像・スクリプト・スタイルシート・通信は、親の CSP の許可先に無いので読めない (#411 のメンテナ決定。外部の教材は許可しない)。回帰は `packages/e2e/tests/browser-preview.spec.ts` (本番の CSP の下では `production-build.spec.ts`)
- **ユーザーの JS / TS は opaque origin の sandbox iframe 内の Worker でだけ実行する (#290 / ADR-0041)**: エディタの realm で eval しない (`new Function` / `AsyncFunction` / `eval` をエディタ側でユーザーコードに使わない)。同じ realm だと停止できず、同期ループでエディタが固まり、親 DOM・localStorage・proof の IndexedDB・`/author` の `#author-jwk` に届く。`executors/sandbox/SandboxRunner.ts` が実行ごとに `sandbox="allow-scripts"` の srcdoc iframe を作り、その中の Blob Worker で動かす。**`allow-same-origin` を足さない** (`runnerDocument.ts` の `SANDBOX_IFRAME_TOKENS`。足すと親と同じ origin になる)。停止・タイムアウト・出力予算の超過・runner の準備応答なしは **iframe の除去**で終わらせ、ユーザーコードの協力を当てにしない。親は `e.source === iframe.contentWindow` と `parseSandboxMessage` (runId と形) を通ったものだけを扱い、Worker は起動時に渡した MessagePort だけで返す。runner の CSP (`default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' blob:; worker-src blob:; connect-src 'none'`) を緩めるときは ADR-0041 を更新する。srcdoc は親の CSP (`config/deliveryHeaders.ts`。#411) も継承するので、**親の CSP で runner の inline script (`'unsafe-inline'`)・blob: Worker・`'unsafe-eval'` を塞がない** (塞ぐと runner の準備応答なしの `error` になる。外すのは runner を専用ページにする #897)。Worker のソース (`workerSource.ts`) はバンドラの変換を受けない文字列定数で、テストは node の `vm` で評価する。`CodeExecutionController` は run ごとに番号を持ち、状態とターミナルへの出力は今の run のときだけ書く (停止 → 即再実行の競合)。E2E はタイムアウトと出力予算を dev 限定の `window.__tcExecLimits` で縮める (本番ビルドでは読まない)。回帰は `packages/e2e/tests/code-execution.spec.ts` と `production-build.spec.ts` (本番の CSP / COEP 下で動くこと)
- **Python (Pyodide) は、エディタのメインスレッドでも同じ origin でも動かさない (#649 / #719 / ADR-0047 / ADR-0056)**: `PythonExecutor` はメイン側のアダプタで、Pyodide は opaque origin の sandbox iframe (`executors/python/PythonRunner.ts`。`sandbox="allow-scripts"` と `allow="cross-origin-isolated"`、srcdoc と CSP は `pythonRunnerDocument.ts`) の中の Blob の classic Worker (`pythonRunnerWorkerSource.ts`。文字列定数) で動く。**`allow-same-origin` を足さない・同じ origin の Worker へ戻さない** (戻すと、実行コードから proof の IndexedDB に届く = #719)。runner が cross-origin isolated でなければ実行しない (fail closed。`allow` の属性を外すと SharedArrayBuffer が使えず、ここで止まる)。opaque origin の Blob からは module Worker を起動できないので classic Worker にし、Pyodide は `importScripts` で読む。Pyodide の stdin のコールバックは同期で返す必要があるので、Worker の中で `Atomics.wait` する。SharedArrayBuffer は runner が作って Worker と共有する (親の SAB は opaque origin へ渡せない)。親は、ターミナルが確定した行と EOF (下の `InteractiveStdin`) を `stdin` / `stdin-eof` で runner へ送る (`stdinChannelSource.ts`)。メインスレッドへ戻すと、`input()` がブラウザの `prompt()` に戻り、計算中にエディタが固まる。**親は受け取ったメッセージを、`e.source`・`e.origin === 'null'`・`parsePythonRunnerMessage` (runner の ID・run の番号・type の許可リスト・型・長さ) で検査し、通ったものも「実行コードの出力」としてしか扱わない** (runner と Worker の中は実行コードの支配下にあり、メッセージは偽装しうる)。親から runner へ渡すのは、コード・パッケージ名・stdin の行・出力の予算だけ (proof・token・鍵・DB 名を渡さない)。CSP は `'unsafe-eval'` を付けず、通信は Pyodide の取得元 (`PYODIDE_CDN_URL`) と micropip 用の PyPI だけ (許可は `pythonRunnerProtocol.ts` の定数から作る。足すなら ADR-0056 を更新する)。出力は Worker がまとめて送り、JS / TS と同じ予算で打ち切る。`PythonExecutor` の側ではエコーも行の編集もしない (#707 で外した。足すと二重エコーになる)。stdout / stderr は `write` ハンドラで逐次渡す。`batched` に戻すと、改行の無い出力 (`input("名前: ")` の案内文) が出なくなる。stdin は `setStdin({ read })` でバイト列として渡す。`stdin` オプションは改行の無い断片に `\n` を足し、autoEOF で EOF を差し込むので、分割した長い行が壊れる。`isatty` は付けない (tty でなければ `input()` は案内文を stdout に書いて flush してから読む。付けると tty 用の別の経路に入る)。**停止・タイムアウト・異常・予算の超過は runner の `terminate()` (iframe の除去)** で行い、次の実行で初期化し直す (`isInitialized` が false に戻る)。タイムアウト (60 秒) は入力待ちの間を数えない。SharedArrayBuffer に依存するので、cross-origin isolation (COOP / COEP) を外すと Python が動かなくなる。srcdoc は親の CSP (`config/deliveryHeaders.ts`。#411) も継承するので、親の CSP で runner の inline script・Pyodide の取得元 (script-src と connect-src)・PyPI・blob の Worker を塞がない (親の CSP は `PYODIDE_CDN_URL` / `PYPI_ORIGINS` を同じ定数から読む)。Pyodide は jsDelivr から取るので、回帰は `packages/e2e/tests/python-isolation.spec.ts` (Pyodide の取得を止めた初期化の失敗だけが PR ゲートで、ほかは `@nightly`)、入力は `code-execution-c-python.spec.ts`、本番ビルドは `production-build.spec.ts` にある
- **Wasmer の `Process.kill()` は、走っている wasm を止めない (#711 の実測)**: `kill()` の後、`wait()` は約 30ms で返り、run は `aborted` で終わって後続 (利用者のプログラムの起動) へは進まない。これは run ごとの `ActiveRun` が保証する。しかし clang の wasm 自体は worker の上で走り続け、本来のコンパイルの終わりまで worker を塞ぐ (重いコンパイルで約 30 秒。`wasmer.close()` もそれを待つ)。無限ループのプログラムも同じで、exit 137 で `aborted` になるが worker は塞がったまま残る。**停止が保証するのは「先へ進まないこと」で、CPU の解放ではない**。直し方 (実行系ごと専用の Worker に入れて terminate する、など) は #711 で未決。回帰と既知の不具合の固定は `packages/e2e/tests/code-execution-c-abort.spec.ts`
- **対話の実行の stdin の行規律はターミナルが持つ (#707)**: `CTerminal` が `terminal/stdinLineDiscipline.ts` でエコー・バックスペース (コードポイント単位)・Enter での確定・Ctrl+D・Ctrl+C を処理し、executor には `executors/interfaces/ILanguageExecutor.ts` の `InteractiveStdin { writeLine, close }` で、確定した行 (LF 付き) と EOF だけを渡す (C / C++ / Python で共通)。**stdin に渡す行と `terminalInput` の記録は、同じ確定した行から作る** (分けると、記録とプログラムが受け取る行がずれる)。C は pipe のままで、Wasmer の tty (`terminal: true`) を足さない (EOF と停止は tty でも解決せず、エコーが二重になる。その代わりプログラムから見て `isatty(0)` は偽)。`pipeInteractiveStdin` は書き込みと close を 1 本の列に並べ、渡した行を届けてから EOF を送る。空の行の Ctrl+D と「入力終了」(`#stdin-eof-btn`) が EOF で、書きかけの行の Ctrl+D は LF 付きの確定だけ。閉じた後の入力は送らず、記録もしない。Ctrl+C は、選択があればコピー (記録しない。xterm に `\x03` を送らせない)、無ければ `^C` をエコーして `CodeExecutionController.abort` (今の run のときだけ)。`<iostream>` を使う C++ は clang のコンパイルが終わらない (#573) ので、C++ の入力の E2E は `<cstdio>` で書いてある
- **C / C++ の実行系は、最初の実行まで読み込まない (#617)**: `executors/c/LazyClangExecutor.ts` の代理 (`getLazyCExecutor` / `getLazyCppExecutor`。シングルトン) を通し、最初の C / C++ の実行と `/author` の検証で、`CExecutor` / `CppExecutor` を `import()` して初期化する。**`CExecutor` / `CppExecutor` / `@wasmer/sdk` を、この代理の `import()` 以外から静的に import しない** (JS だけの起動で Wasmer の SDK と glue が読まれ、起動のたびに clang の webc 約 110 MB を取りに行く形に戻る。`WasmerSdkCorruptedError` は `executors/c/errors.ts` から import する)。**起動時に初期化を戻さない・言語の選択では初期化しない** (新しいタブの既定の言語が C なので、選択で起こすと毎回の起動で走る)。並行する `initialize()` は代理が 1 つの Promise にまとめ、失敗は待っている全員に返して捨て、次の `initialize()` がやり直す。`abort()` は初期化 (ダウンロード) を止めず、初期化待ちの間に止めた run は controller の `isCurrent()` で先へ進まない (#711 と同じ契約)。見張りは `packages/e2e/tests/c-runtime-lazy.spec.ts`・`production-build.spec.ts` の #617・model E2E
- **非対話の実行 (一括検証の基盤) は対話の実行の挙動を変えない (#802 / ADR-0051)**: `executors/nonInteractive/runNonInteractive.ts` は `ILanguageExecutor.run` の第 3 引数 `ExecutionOptions` (`stdin`・`showLastValue`) で C / C++ / Python を走らせ、stdout と stderr を別々の文字列で返す。`stdin` を指定したときだけ、C / C++ は pipe に全体を書いて閉じ (`onStdinReady` を呼ばない)、Python は行チャネルに積んで `StdinChannelWriter.close()` で EOF を渡す (エコーも line discipline も通さない)。**対話の実行は `close()` を呼ばず、`showLastValue` は既定 (true) のまま**。実行時間の上限 `NON_INTERACTIVE_TIMEOUT_MS` はこの入口だけのもので、`onProgramStart` (利用者のプログラムが動き始めた合図) から数える (コンパイル・ランタイムの読み込みは数えないので、コンパイルが終わらないと上限は働かない)。打ち切りと中止は、結果を先に確定してから停止ボタンと同じ `executor.abort()` を呼ぶ (停止の通知を stderr に混ぜないため)。打ち切った次の実行はランタイムの作り直しを待つ。既定の executor は対話の実行と共有するシングルトンなので、**ターミナルの実行と同時に走らせない** (画面側で排他にする。#799)。`authoring/verification/` の比較 (`compareOutput.ts`。仕様 §4.10 の `trim` / `exact`) と一括の実行器 (`runBatchVerification.ts`) は、結果を proof にも教材フォルダにも記録しない。検証の画面 (#799) は `AuthorPage` が `ExecutionLock` で排他にする (検証中は `#author-run-btn` を止め、ターミナルの実行中は検証を `blocked` / `terminal-busy` にする。ターミナルの実行は `#author-stop-btn` で止める = #820)。対象の内容は `AuthorWorkspace.readCurrentText` で読む (開いている文書は今のテキスト、それ以外はフォルダ。開いている文書のファイルを裏で読み直さない)。実物の実行の入口 (`runNonInteractive`) は最初の検証で dynamic import する。コンパイルが終わらない解答には自動の上限が無く、中止で抜ける (ADR-0051)
